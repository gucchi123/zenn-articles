毎日動画を自動生成する個人プロジェクトを運用しています。ナレーションをTTSに任せると、すぐにぶつかる問題があります。**生成のたびに声が微妙に違う**ことです。

視聴者にとって「チャンネルの声」はブランドそのものです。昨日と今日で声が変わると、同じシリーズの動画でも別物に見えてしまう。かといって毎回人間が録るのはスケールしません。

解決策はシンプルでした。**声を一度だけ「設計」し、以後はその声をzero-shotクローンで複製し続ける**。OSSの [Irodori-TTS](https://github.com/Aratako/Irodori-TTS) でこの運用を数ヶ月回してきたので、パイプライン設計と、実際に踏んだ罠をまとめます。

![声の設計→正本→複製パイプライン全体像](/images/irodori-voice-clone-pipeline.png)

## Irodori-TTSの2つのモデルを使い分ける

Irodori-TTSはFlow Matchingベースの日本語対応TTSで、役割の異なる2系統のチェックポイントがあります。

| モデル | 役割 | 使う頻度 |
|---|---|---|
| `Irodori-TTS-600M-v3-VoiceDesign` | **声を作る** — テキストキャプションから声そのものを設計 | 最初の1回だけ |
| `Irodori-TTS-500M-v3` (base) | **声を使い回す** — 参照音声からzero-shotクローン | 毎日・全動画 |

この分担が肝です。VoiceDesignは「30代くらいの落ち着いた女性の声、少し早口、明るいトーン」のような**文章から声を生成**できます。つまり、**実在の誰の声でもない声**をゼロから作れます。

## Step 1: 声を「設計」して正本を決める

VoiceDesignで候補を複数生成し、聴き比べて1本だけ承認します。承認したWAVは以後いっさい変更せず、**正本(canonical reference)として1ファイルだけ**残します。

ここで意識したのは、**実在の人の録音を複製元にしない**ことです。オリジナルに設計した声なら、パブリシティ権やなりすましの問題を構造的に回避できます。「誰かの声に似せる」必要は、ナレーション用途では最初からありません。

## Step 2: zero-shotクローンで量産する

量産フェーズはbaseモデル1本です。正本WAVを`--ref-wav`に渡すだけで、毎回同じ声で任意のテキストを読み上げます。

```bash
python infer.py \
  --hf-checkpoint Aratako/Irodori-TTS-500M-v3 \
  --text "こんにちは。今日は通信費の見直しについて話します。" \
  --ref-wav outputs/canonical_voice.wav \
  --output-wav out/scene_01.wav \
  --seed 42
```

ポイントは2つ:

- `--ref-wav`は**毎回同じ正本ファイル**を指す。台本ごとに変えない
- `--seed`を固定すると声質・話し方のブレがさらに減る(うちは全動画seed=42)

v3系は出力長を自動推定してくれるので、`--seconds`の手動指定も不要です。

## 実運用で踏んだ罠3つ

ここからが本題です。技術的には上の2ステップで完成ですが、**運用に組み込むと事故は「コードの外」で起きます**。

![実運用で踏んだ3つの罠と対策](/images/irodori-voice-3-traps.png)

### 罠① 正本ドリフト — 別人の声のまま公開した

新チャンネル用にパイプラインを複製・派生させたとき、コピー元の`REF`パスがそのまま残っていて、**別チャンネルの声のまま動画を2本公開してしまいました**。

声はdiffに出ません。コードレビューでは`REF = .../voice.wav`の1行は「正しく見える」。気づいたのは公開後でした。

対策:

- 正本は**チャンネルごとに1ファイル**をフルパスで固定し、スクリプト内に「なぜこのREFか」をコメントで残す
- パイプライン派生時の**チェックリスト**を作る(声REF・配色・マスコット・テロップ様式・タイトル書式)。派生作業は「コードのコピー」ではなく「設定の棚卸し」だと考える

### 罠② 誤読は「共通辞書 + かな書き」の二段構え

TTSは固有名詞を平気で誤読します。うちで実際に動画に載ってしまったのは「楽天市場 → らくてん**しじょう**」型の誤読です。

対策は二段構えにしました。

**一般名詞・固有名詞 → 共通発音辞書。** 置換辞書(JSON)を1個だけ用意し、**全パイプラインが必ずこれを通してからTTSに渡す**構成にします。辞書を複数持つと、修正がパイプラインごとに分岐して事故ります(これも一度やりました)。

**助数詞 → 台本データ側でかな書き。** 「1月」は「いちがつ」とも「ひとつき」とも読み、**文脈でしか決まらない**ので辞書では扱えません。台本データに読み専用フィールドを持たせて分離します。

```json
{
  "narration": "1月の請求額はここで確認できます",
  "tts": "いちがつの請求額はここで確認できます"
}
```

字幕には`narration`(漢字)、TTSには`tts`(かな)を渡す。表示と読みを分けるだけで助数詞問題はほぼ消えます。

### 罠③ コールドスタートを故障と誤診しない

初回推論は、モデルのダウンロードと初期化で**1行目の出力まで15〜30分無音**になることがあります。これを「ハングした」と誤診してプロセスをkillすると、やり直しでさらに時間が溶けます(一度これで1時間以上無駄にしました)。

対策は「知っておく」ことと、**先にジョブキューを組み切ってから投入する**こと。ウォームアップ後の2行目以降は数十秒/行で流れます。

## 検品も自動化する — faster-whisperで逆起こし

誤読対策をしても、辞書に無い新語は必ず漏れます。最後の関門として、**合成した音声を機械で聞き直して台本と突き合わせる**工程を入れています。

```python
from faster_whisper import WhisperModel

model = WhisperModel("large-v3", device="cpu", compute_type="int8")
segments, _ = model.transcribe(
    str(wav), language="ja",
    condition_on_previous_text=False,  # ← 重要
)
text = "".join(s.text for s in segments)
```

`condition_on_previous_text=False`は必須級です。既定のTrueだと、短いナレーション音声で**同じ文を延々繰り返すハルシネーションループ**が起き、照合が誤検知だらけになります。

なお、逆起こし側(Whisper)も誤認識するので**完全一致は求めません**。固有名詞と数字に絞って照合すると、実用的な精度で「動画に載る前」に誤読を捕まえられます。

## 倫理面: 「作った声」だから安心して回せる

声のクローン技術は使い方を間違えると加害になります。運用ルールとして守っているのは次の3つです。

- **他人の実声を無断でクローンしない。** パブリシティ権の問題に加え、なりすまし・詐欺への悪用と区別が付かなくなる。本人の声を使う場合は本人の明示的な同意が前提
- **AI音声であることの開示**はプラットフォームの規約に従う
- Irodori-TTSは生成音声に[SilentCipher](https://github.com/sony/silentcipher)の音声透かしが自動で入る(対応環境)。**検出可能性を壊さない**

そもそも今回の構成は「実在しない声をVoiceDesignで設計する」ところから始めているので、権利面で一番筋がよい形だと思っています。ナレーション用途で「誰かに似た声」が必要な場面は、実はありません。

## まとめ

- 声の一貫性は**正本1ファイル + seed固定**で作る。台本ごとにrefを変えない
- 事故はコードの外で起きる。**派生チェックリスト・共通発音辞書・逆起こし検品**の3つの仕組みで塞ぐ
- 声はチャンネルのブランド。TTS導入の最初に「声の管理設計」をやっておくと、あとが全部楽になります
