個人の自動化プロジェクトで、SNSの検索APIを叩いて「あるテーマについて投稿している人」を探し、候補として並べるCLIツールを回している。

そのツールが3日連続でこう言った。

```
候補 0件 (検索語: ○○ 比較 / 直近3日)
```

例外なし。終了コード0。ログにも異常なし。

私はこれを「この話題を投稿している人が、この面にはもういない」と読んだ。検索語を練り直し、そもそもこのチャネルを畳むべきかを検討し始めた。

**全部見当違いだった。** 0件は面のせいではなく、私が渡したフラグのせいだった。しかも原因の切り分けを不可能にしていたのは、私自身が書いた `print` の一行だった。

![同じ --limit が、パイプラインの逆の端に刺さっていた](/images/zero-results-denominator.png)
*入口を絞るか出口を絞るかで、同じ `--limit 3` の意味が変わる*

## 症状

再現するとこうなる。実際に叩いていたコマンドはこれ。

```bash
py -3.12 follow.py --search "○○ 比較" --limit 3 --max-age-days 3
```

「候補は3件くらい見れば十分」「直近3日の投稿だけ見たい」というつもりだった。

出力は前掲のとおり `候補 0件`。何も壊れていないように見える。

## 原因1: `--limit` が入口を指すか出口を指すかは、名前からはわからない

同じディレクトリに、同じAPIを叩く姉妹ツールが2本ある。数週間ずれて書いた。両方に `--limit` がある。

**返信用のツール:**

```python
ap.add_argument("--limit", type=int, default=8, help="1回に作るドラフト数")
```

```python
def _search(cfg, q, limit=100):          # ← 取得数は内部で固定
    return api(cfg, "searchPosts", {"q": q, "limit": limit, "sort": "latest"})

...
cands = cands[:a.limit]                  # ← --limit は「出口」を絞る
```

**フォロー用のツール:**

```python
ap.add_argument("--limit", type=int, default=25)
```

```python
def search(cfg, q, limit, max_age_days=45):
    r = _get(cfg, "searchPosts",
             {"q": q, "limit": limit, ...})   # ← --limit がそのままAPIへ = 「入口」
```

同じ名前が、**同じパイプラインの逆の端**に刺さっている。

- 返信ツールで `--limit 3` = 100件取ってきて、ドラフトを3本作る → 妥当
- フォローツールで `--limit 3` = **APIから3投稿しか取ってこない**

そして取得した3投稿は、この後の絞り込みを通る。

```
取得 3投稿
  → 自分の投稿を除く
  → 既にフォロー済みを除く
  → 45日(このとき3日に狭めていた)より古いものを除く
  → 関門(除外ルール)で落とす
= 0
```

3投稿しか入れなければ、まっとうなパイプラインでも0が出る。バグではない。仕様どおりに0を返している。

既定の `--limit 25` で回したら、その場で候補は5件出た。

## 原因2: 出口の数しか表示していなかったので、0の出どころがわからない

これが本当の原因だと思っている。当時の表示はこう書いてあった。

```python
print("候補 %d件 (検索語: %s / 直近%d日)" % (len(rows), q, max_age_days))
```

**分子しか出していない。** `候補 0件` という文字列は、次のどれとも整合してしまう。

| 実際に起きていること | 正しい対処 |
|---|---|
| 検索語がヒットしなかった (取得0件) | 検索語を変える |
| 3投稿しか取っていない | **フラグを直す** |
| 25投稿取ったが全部古い | 期間を広げる |
| 25投稿取ったが全部関門で落ちた | 関門を疑う |

対処が全部違う。私は表の1行目だと決めつけて、2行目を3日間放置した。

さらに悪いことに、この誤診は**症状を深くする変更**を生んだ。「候補が古い人ばかりだから絞ろう」と考えて `--max-age-days` を45から3に狭めていた。分母を見ないまま打った対策が、もともと少なかった入力をさらに削っていた。

0 は例外を投げない。もっともらしい値としてパイプラインを通り抜ける。**だから 0 は、自分がどこから来たかを自分で説明できなければならない。**

## 対処1: 分母と、落とした理由の内訳を必ず出す

表示をこう変えた。

```python
n_posts = len(r.get("posts", []))
print("取得 %d投稿 → 候補 %d件 (検索語: %s / 直近%d日)"
      % (n_posts, len(rows), q, max_age_days))

# 🔴 分母が小さいときは、原因になっているフラグの名前を出力に書く
if n_posts < 20:
    print("   ⚠️ 取得が %d投稿しかない。--limit は**取得数**なので、"
          "小さいと候補が出ない。既定は 25" % n_posts)

if old:
    print("   ⚠️ %d件は %d日より古いので除外した" % (old, max_age_days))

if dropped:
    print("   -- 関門で除外 %d件 --" % len(dropped))
    for h, why in dropped[:8]:
        print("      @%-28s %s" % (h[:28], why))
```

出力はこうなる。

```
取得 25投稿 → 候補 5件 (検索語: ○○ 比較 / 直近45日)
   ⚠️ 6件は 45日より古いので除外した
   -- 関門で除外 4件 --
      @xxxxxxxx                     NG語:除外ワード
      @yyyyyyyy                     NG語:宣伝文
```

25 → 5 の間に消えた20件が、全部理由つきで見える。次に0件が出たとき、読む人はどの段で消えたかを一目で切り分けられる。

閾値つきの警告(`n_posts < 20`)は特に効いた。**原因になっているフラグの名前を、エラーメッセージ側に書いてある**からだ。半年後の自分は `--limit` の意味を絶対に覚えていないが、出力を読めば気づく。

## 対処2: 入口と出口に、別の名前を与える

```python
# 名前は互換のため残し、別名と説明を足して取り違えを防ぐ
ap.add_argument("--limit", "--fetch", type=int, default=25, dest="limit",
                help="検索APIから取得する投稿数(候補数ではない)。小さくすると候補が激減する")
ap.add_argument("--show", type=int, default=12, help="画面に出す候補の件数")
```

やったことは3つ。

1. **入口に `--fetch` という別名を足した。** `limit` という語は入口も出口も指せるが、`fetch` は入口しか指さない
2. **help に「候補数ではない」と否定形で書いた。** 取り違えの方向がわかっているなら、それを明示的に否定するのが一番効く
3. **出口を `--show` として分離した。** これまで表示件数は `ranked[:12]` とハードコードだったので、そもそも出口を指定する手段がなかった。「出口を絞りたい」人が `--limit` に手を伸ばす動機を消した

argparse の小さな注意点として、複数のオプション文字列を渡すと `dest` は最初の長いオプションから導出される。ここでは `--limit` が先なので `dest="limit"` になるが、順序を入れ替えた瞬間に既存の呼び出し側が壊れるので、明示しておくほうが安全だ。

## この形はどこにでもある

「入口の上限」と「出口の上限」に同じ語を使ってしまう事故は、この手のツールに限らない。

```sql
-- 内側の LIMIT は「集める量」、外側は「返す量」。片方だけ絞ると結果が消える
SELECT * FROM (SELECT * FROM posts ORDER BY created_at DESC LIMIT 10) t
WHERE t.score > 3 LIMIT 10;
```

- ページャの `per_page` と、フィルタ後の表示件数
- スクレイパの「巡回するページ数」と「抽出するレコード数」
- `head -n 100 | grep ERROR` の `-n` は入口、`| head -n 10` は出口

共通するのは、**`fetch(N) → filter → filter → take(M)` という形をしたコードが、M しか報告しない**という点だ。M だけを見ていると、Mが小さいのは「世の中にそれしかない」のか「Nが小さい」のか「フィルタが厳しい」のかが永久に区別できない。

なお、返信用ツールのほうの設計(取得数は内部で固定100、ユーザーが触るのは出口)は、結果的に安全だった。**利用者が頭の中で数えているのは出口の数**なので、外に出す1個のつまみは出口に付けるのが素直だ。入口も外に出す必要があるなら、`fetch` と名乗らせる。

## 教訓

- **`limit` はパイプラインのどちらの端も指せる語なので、単独で使わない。** 入口は `fetch`、出口は `show` / `take` と書き分ける。特に同じディレクトリの姉妹ツールで、同じ語を逆の意味に使わない
- **0件は例外を出さない。** もっともらしい値として通り抜けるので、0 のほうにこそ由来を持たせる。分子だけでなく分母を出す
- **絞り込みの各段で落とした件数を黙って捨てない。** 「何件を、なぜ落としたか」を出せば、0件の切り分けは読むだけで終わる
- **分母を見ないまま打つ対策は、原因ではない場所を触る。** 私の場合は期間をさらに狭めて、入力不足を悪化させた
- **警告文には、原因になっているフラグの名前をそのまま書く。** 未来の自分は仕様を覚えていないが、出力は読む
