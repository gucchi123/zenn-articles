Karpathy が 10/2 に、LLM の出力を理解するための形について書いていました。要点は次の4つです。

- 文章なら、ASD-STE100（航空整備マニュアル向けの制限言語）で書かせると読みやすい
- それより図のほうが読みやすい
- それより HTML のほうが読みやすい
- いちばん期待しているのは、テーマごとに作る解説動画

元の投稿: https://x.com/karpathy/status/2105819303471976479

自分は個人プロジェクトで、AIエージェントに約30媒体の発信を任せています。毎朝エージェントが「Individual Report」という運用レポートを書き、それを読んで判断するのが日課です。そこで 10/3 の朝のレポートを4つの形にしてみました。

先に結論を書くと、いちばん効いたのは図でした。症状ごとに足していた打ち手が、根本への1つにまとまりました。

## 題材：10/3 の朝に重なった障害

レポートには課題が6つ並んでいました。そのうち次の3つが今回の題材です。

- PC の C ドライブが 0GB になった（07:20 時点）
- 週2回の動画づくり（Mizu643）が描画 38% で容量不足（ENOSPC）になり失敗した（03:10）
- 投稿用のブラウザ（CDP 9444）に接続できなくなり、自動の再起動も時間切れになった

レポートの地の文はこうです。

> 10/2 14時は空き 22GB。夜〜朝にページファイルが 43.6GB（使用は 8GB）まで広がり、Mizu643 の描画が作った 6GB のバンドル（02:44）が失敗後も残り 0GB に。04:30 の掃除タスクは「2時間以内のものは残す」ため、そのバンドルを消さずに rc=2（空き 3.6GB）。根本はメモリ不足（空き 1.3〜3GB）でページファイルが膨らむこと。

間違ってはいません。ただ1文に事実が3つ入っていて、何をすればいいかは最後まで読まないと出てきません。

## 文章だけで動いていた2日間に起きたこと

10/2〜10/3 の朝は、この文章のレポートを読んで、症状ごとに手を打っていました。

| 日時 | 打ち手 | 結果 |
|---|---|---|
| 10/2 09:47 | ディスクが埋まったので、一時ファイルの掃除タスクを新しく追加 | 9/26 からある掃除タスクと役割が重複していた |
| 10/2 11:21 | ブラウザが固まったので、毎時の見回り（接続確認→だめなら再起動）を追加 | 10/3 07:32〜07:38 に再起動を3回試して、3回とも失敗 |
| 10/3 朝 | — | C 0GB・動画失敗・ブラウザ停止が再発 |

打ち手は3件で、止まった障害は0件でした。

## 1. 文章：ASD-STE100 に 80% 寄せる

STE の規則をそのまま日本語に当てると硬すぎます。Karpathy も書いていたように「8割くらい」に緩めました。使ったプロンプトです。

```text
次のレポートを、ASD-STE100 の規則に 80% 寄せて日本語で書き直してください。
- 1文に1つの事実だけを書く。主語を省かない
- 能動態で書く。手順は番号付きの命令形にする
- 同じものは同じ言葉で呼ぶ（言い換えない）
- 最初に「状態」、次に「原因」、最後に「手順」を書く
```

出てきたものです。

> C ドライブが満杯です。空きは 0GB です。
> 原因はページファイルです。大きさは 43GB です。メモリが足りないと、ページファイルが大きくなります。失敗した描画が、6GB のキャッシュを残しました。
> 次の順に作業してください。1. PC を再起動します。2. Mizu643 の描画をやり直します。3. 9444 のブラウザが起動したことを確かめます。

変わったのは、自分に頼む作業の順番でした。前のレポートでは「再起動」の理由が課題1〜3に散らばっていて、何から手をつけるかが分かりにくかった。STE に寄せたら、最初の手順が再起動になりました。

## 2. 図：症状を並べず、共通の原因に向かう矢印で描く

```text
次のレポートの課題を、因果の図（SVG）にしてください。
- 症状を横に並べない。共通の原因から矢印が出る形にする
- 根本の原因は1色、今朝の障害は赤、見逃していた設定は点線にする
- 各ノードに、根拠になる数字（時刻・GB・件数）を1つだけ書く
```

![因果の図](/images/llm-output-formats-causal.png)

6つの課題のうち3つが、1本の線でつながりました。根っこはメモリ不足です。メモリが足りないと Windows がページファイルを広げ、ディスクが尽き、ブラウザも重くなります。

ここで初めて、前日に足した掃除タスクが既存のものと重複していることに気づきました。本当に直すべきだったのは、既存タスクの「2時間以内のものは残す」という基準でした。

## 3. HTML：原因の鎖を押すと、根拠と打ち手が出る

毎朝のレポートは長い表の連続になりがちです。そこで、原因の鎖をボタンにして、押した所だけ「何が起きた／なぜ／打ち手」が出るページにしました。データの形は単純です。

```js
const D = {
  mem:  { what: "32GB 中の空きが 1.3〜3GB", why: "ブラウザと処理が重なる", act: "PC を再起動" },
  pf:   { what: "割り当て 43.6GB・使用 8GB", why: "メモリ不足の間に自動で拡張", act: "再起動で戻る" },
  disk: { what: "07:20 に 0GB", why: "ページファイル＋描画キャッシュ 6GB", act: "掃除の基準を 1時間に" },
  // …
};
```

数字のタブ（週ごとの到達数など）と障害のタブを分けたので、読む側が順番を決められます。

## 4. 動画：台本と絵コンテを渡す

動画は 60〜80秒、6場面にしました。場面の静止画（HTML から PNG）と、ローカルの音声合成（Irodori-TTS）を ffmpeg でつなぐ軽い構成です。いつもの描画（Remotion）は重く、今朝まさにそれが容量不足で落ちていたので、使っていません。

## 実行結果はどう変わったか

![前後の比較](/images/llm-output-formats-before-after.png)

| | 文章のレポートだけ（10/2〜10/3朝） | 図にした後（10/3 07:54〜） |
|---|---|---|
| 打ち手 | 症状ごとに3件 | 根本に1件（PC の再起動を最優先に） |
| 同じ原因と分かった課題 | 0（6つが別々） | 6つのうち3つ |
| タスクの整理 | 既存と同じ役割の掃除タスクを1本追加 | 重複を削除。既存の基準を 2時間→1時間 |
| 障害は止まったか | 止まらず（再起動3回失敗） | メモリを空けたらブラウザは1回で復旧 |

その後、ほかのアプリを閉じてメモリを空けました（空き 1.3〜2.7GB → 8.3GB）。3回失敗していたブラウザの起動は、空けたあと1回で通りました。ディスクの空きは 15.8GB。ページファイルはまだ 43.8GB のままなので、完全な再起動のあとに縮むかを確かめます。

## まとめ：形は「読んだ人が次に何をするか」で選ぶ

| 形 | 効いた場面 |
|---|---|
| STE に寄せた文章 | 手順や判断を頼むとき |
| 因果の図 | 複数の症状に共通の原因があるとき |
| HTML | 数字と事情を行き来したいとき |
| 動画 | 前提のない人に流れを渡すとき |

エージェントの出力が増えるほど、監督する側の負担はこの選び方で変わる気がしています。少なくとも、症状ごとに手を足していくエージェントを止められたのは、今回は図でした。
