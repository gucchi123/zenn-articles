個人プロジェクトで、生成AIのエージェントに30近い媒体の発信と計測を任せている。定期実行のタスクは100本を超えていて、毎朝ざっと「失敗したタスク」の一覧を見るのが習慣になっている。

ところがこの1週間で見つけた不具合は、4つのうち3つが**その一覧に載らない形**で起きていた。終了コードは0、画面は緑、数字もそれらしく出ている。それでも中身は失敗していた。残りの1つは一覧に載っていたのに、原因が自分の変更だと結びつくまで時間がかかった。

この記事は、その4つと、それぞれをどう見つけて、どう直したかのメモ。

![4つの失敗で「見えていたもの」と「実際」](/images/green-but-failed-four-cases.png)

## 1. 終了コード0なのに、つながり申請が1件も送れていなかった

承認済みの5人にSNSのつながり申請を送る定期実行を仕込んでいた。朝の実行は終了コード0。タスク一覧でも成功扱いだった。

ログを開くと、5件とも結果が `unverified` になっていた。プロフィールを開き直すと、申請ボタンがまだ「つながる」のまま残っている。**1件も送れていなかった。**

原因は2つ重なっていた。

- 申請ボタンを押したあとに出る確認ダイアログの文言が変わっていた。スクリプトは旧文言のボタンだけを探していたので、何も押さずに先へ進んでいた
- 送れたかどうかの確認に使っていた「保留中」の表示が、プロフィールから出なくなっていた

スクリプトは「確認できなかった」ことをちゃんと `unverified` と書いていた。ただ、**書いたうえで終了コード0を返していた**。スケジューラが見るのは終了コードだけなので、誰も読まないログの中でだけ失敗していたことになる。

直したのは3点。

```js
// 確認ダイアログのボタンは文言の候補を複数持ち、role 属性に頼らない
const noNote = p.locator('button:visible')
  .filter({ hasText: /^\s*(挨拶なしで送信|メッセージなしで送信|Send without a note)\s*$/ }).first();

// 成立の確認は、画面の表示ではなく「送信済み一覧」に名前があるかで見る
await p.goto('https://www.linkedin.com/mynetwork/invitation-manager/sent/');
const pending = await p.evaluate(n => document.querySelector('main').innerText.includes(n), person.name);

// 未確認が1件でもあれば非0で終わる
process.exit(results.some(r => r.result !== 'sent') ? 2 : 0);
```

「未確認」と書くところまでは作っていても、それを**失敗として外に出す**ところまでつながっていないと、成功と同じ扱いになる。

## 2. 文書の見出しを整えたら、それを読む自動化が止まった

毎日、エージェントに進捗レポートを書かせている。人が読むための文書なので、見出しを「結論」「今日の対応」「学び」の形に整えた。

数日後、別のタスクが止まっていた。週に1回、そのレポートから素材を抜き出して投稿の下書きを作るタスクで、抜き出しに使う正規表現が**旧来の見出し**を探していた。

```python
m = re.search(r"## ① This Week's Action.*?(?=\n## [^#])", text, re.S)
```

新しい見出しには1つも当たらず、素材は0字。下書きが作られないまま「承認待ちの在庫」が減っていった。人の確認を挟む発信は在庫が切れると止まるので、実害に一番近い型だった。

こちらは終了コード1で落ちていたので、失敗の一覧には載っていた。ただ、原因が「自分がレポートの見た目を変えたこと」だとは、すぐには結びつかなかった。

直し方は2方向。

- 抜き出し側が、新旧どちらの見出しでも素材を拾えるようにした
- レポート側にも、旧来の見出しを残した

見出しを変える前に `grep -rn "## ①" --include=*.py` のように**その文書を読んでいる側を先に探す**、を手順に足した。人が読む文書でも、どこかの仕組みの入力になっていることがある。

## 3. 「人のクリック」の数え方が、道具ごとに違っていた

リンクのクリックを、自前のリダイレクト（Cloudflare Workers + D1）で記録している。同じ期間（10日分）のクリックを2つの集計スクリプトで数えたら、**76 と 23** と3倍以上違った。

生ログを1行ずつ見ると、76 のほうには次が混ざっていた。

| 混ざっていたもの | 見分け方 |
|---|---|
| クラウド事業者の IP からのアクセス（AWS・GCP など）| IP の先頭で判定。referrer 空のものが多い |
| Meta のクローラー | 同じ1秒に5件。スマホの UA を名乗るが、IP は Meta の帯 |
| referrer が空のアクセス | 実ブラウザからのクリックはほぼ referrer を持つ |

どちらのスクリプトも「bot を除外している」つもりだった。ただ、除外の条件がそれぞれに書かれていて、片方だけが緩かった。

直したのは、除外する IP の一覧を2つのスクリプトで同じものにしたこと。「人とは何か」の定義を1か所に寄せないと、同じ期間の数字が道具によって変わる。

## 4. 候補一覧の抜粋だけ読んで返信し、相手の条件を読み落とした

SNS で「こういう相談をしている人」を集めて一覧にし、それを見て返信を書いている。一覧は1件あたり本文を160字で切っていた。

ある相談に「支払いは先にクレジットカードへ切り替えておくと安心です」と返した。送ったあとで投稿を開き直すと、最後の一文が「できればクレジットカード決済は避けたいのですが」だった。160字の外にあった条件を読み落としていた。

すぐに自分の返信の下へ訂正を付けた（カードを使わずに続けられる方法を、公式の対応状況を確かめてから）。

相談の投稿は、条件（避けたいこと、予算、端末）が最後に来ることが多い。**抜粋は「候補にするか」を決める材料で、答えを書く材料ではない。**一覧の抜粋を400字に広げたうえで、送信前に必ず投稿ページを開いて全文を読む、を手順に入れた。

## 4つに共通していたこと

| | 見えていたもの | 実際 | 見つけたきっかけ |
|---|---|---|---|
| 1 | 終了コード0 | 5件とも未送信 | プロフィールを開いて、ボタンが残っているのを見た |
| 2 | レポートは読みやすくなった | 下流の抜き出しが0字 | 失敗タスクの一覧を1本ずつ開いた |
| 3 | bot 除外済みの数字 | 3倍の水増し | 同じ期間を2つの道具で数えて比べた |
| 4 | 条件に合う候補 | 条件の後半が切れていた | 送信後に全文を開き直した |

どれも「処理が成功したか」ではなく「**成果物がそこにあるか**」を見に行って初めて分かった。終了コードやステータスは、処理が最後まで走ったことしか教えてくれない。

今は、次の3つを決まりにしている。

- **未確認は失敗として外に出す。** ログに書くだけでは誰も読まない
- **成立の確認は、画面の表示ではなく一覧や API で見る。** 表示は予告なく変わる
- **同じものを数える道具が2つあるなら、定義を1か所に寄せる**

エージェントに任せる範囲が広がるほど、「成功と表示されているもの」を疑う作業が人間の側に残る。その作業を少しずつ仕組みに移していくのが、今のところの運用の中心になっている。
