個人の自動化プロジェクトで、ブラウザを操作するエージェントに SNS の返信を入力させている。エディタの入力欄に `type` で本文を打ち込み、送信ボタンを押す、それだけの処理だ。

ある日、送信の直前に入れておいた検査がこう鳴った。

```
5文字目で違う: 入った='を' 期待='1' / 長さ 178 vs 190
```

打ったはずの本文と、入力欄に実際に入った本文が **12文字ずれていた**。

消えていたのは、**半角英数字だけ**だった。

## 症状

このときの実測がこれだ。

```
送ったつもり: 「このまま14を使い続ける」…3つの案…バッテリー89%…iCloudは容量を下げて
実際に入った: 「このままを使い続ける」…  つの案…バッテリー  …  は容量を下げて
```

`14` `3` `89` `%` `iCloud` — 数字も英単語も、全部消えている。日本語は1文字も落ちていない。

一番たちが悪いのはここだ。**残った文が自然な日本語に見える。**

「このままを使い続ける」は少し変だが読み流せる。「バッテリーなら」「は容量を下げて」も、目で追うだけなら文として成立してしまう。エラーも例外も出ないし、入力欄には確かに文字が入っている。スクリーンショットを撮って眺めても「入っているな」で終わる。

そして5日後、同じ罠をもう一度踏んだ。今度は数字が主役の返信で、金額と回数と容量を含む**10個のトークンが全部消えた**。桁区切りのカンマを含む金額も、単位付きの数値も、まとめて落ちた。送っていたら、意味の壊れた文章を公開していたことになる。

## 切り分け — 誰が落としているのか

最初は「このエディタは ASCII を受け付けない仕様なのでは」と疑った。リッチテキストエディタは `contenteditable` の上に独自の入力処理を載せていることが多いので、ありそうな話に思えた。

3つの経路で同じ本文を入れて比べた。

| 入れ方 | 結果 |
|---|---|
| 自動化ツールの `type` アクション | 🔴 半角英数字だけ消える |
| 人がキーボードで打つ | ✅ 全部残る |
| 公式 API から投稿する | ✅ 全部残る |

![3経路で同じ本文を入れて比べると、落ちるのは type だけだった](/images/browser-type-drops-ascii.png)
*同じ本文を3経路で入れた結果。日本語は無傷で、半角英数字だけが消える*

**エディタの仕様ではなかった。** 人が打てば `14` も `iCloud` も無傷で残る。落ちるのは `type` を経由したときだけだ。

つまりこれは「送信先の制約」ではなく「**入力経路の欠落**」で、切り分けを間違えると対処も間違える。実際、最初に「エディタ側の問題」と大きく括ってしまい、一度は「このエディタには自動で送れない」と結論を出しかけた。原因を大きく括ると、直し方を見失う。

確かめられた範囲での推測はこうだ。日本語を入力欄に入れるとき、自動化ツールは1文字ずつのキーイベントではなく、IME の変換確定に相当する経路（`compositionend` / `beforeinput` 系）でまとめて流し込む。エディタ側はこの経路を受け入れる。一方、ASCII は素のキーストロークとして別経路で流れ、エディタの入力ハンドラがそれを取りこぼす——両方の経路を使うから、**片方だけが消える**。

ここは実測で裏を取れていないので断定はしない。ただ「全部消える」でも「全部残る」でもなく **ASCII だけが消える**という選択的な壊れ方は、単一の経路では説明がつかない。

## 対処1 — 送信前に完全一致で突き合わせる

この事故を捕まえたのは、送信前の検査だった。逆に言うと、**検査が無ければ確実に送っていた**。

重要なのは、長さの比較では足りないという点だ。190字が178字になっても、`len()` を目視で比べる運用では気づけない。実際に書いたのはこれだ。

```python
def check(typed: str, expected: str) -> str | None:
    """入力後の実物と期待値を突き合わせる。問題なければ None。

    長さだけでは足りない。何文字目でどう違うかまで出す。
    """
    if typed == expected:
        return None
    for i in range(max(len(typed), len(expected))):
        a = typed[i] if i < len(typed) else "(無)"
        b = expected[i] if i < len(expected) else "(無)"
        if a != b:
            return (f"{i}文字目で違う: 入った={a!r} 期待={b!r} / "
                    f"長さ {len(typed)} vs {len(expected)}")
    return f"長さが違う: {len(typed)} vs {len(expected)}"
```

呼ぶ側はこうなる。読み戻して、一致しなければ送らない。

```python
type_into(editor, body)
typed = read_back(editor)          # 入力欄の実物を取り直す
err = check(typed, body)
if err:
    raise RuntimeError(f"入力が欠落した: {err}")
submit()
```

`read_back` を挟むところが肝で、**自分が投げた値ではなく、相手側の状態を読む**。ここを省略して「`type` が例外を出さなかったから入ったはず」と扱うと、今回の欠落は素通りする。

UI 自動化の書き込み系アクションは、たいてい「操作を送った」までしか保証しない。成功を返すことと、意図した状態になったことは別だ。

## 対処2 — 落ちない文字に寄せる

検査は事故を止めるが、送れるようにはならない。そこで「何なら落ちないか」を測った。

**全角なら落ちない。** `４１０` `ＳＩＭ` `２，１７８` を入れると無傷で残る。日本語が落ちないのと同じ理由で、全角文字は消えない経路を通っているらしい。

なので、送信前に半角英数字を全角へ寄せる小さなモジュールを置いた。

```python
import re

_ASCII = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz,."
_FULL = ("０１２３４５６７８９"
         "ＡＢＣＤＥＦＧＨＩＪＫＬＭＮＯＰＱＲＳＴＵＶＷＸＹＺ"
         "ａｂｃｄｅｆｇｈｉｊｋｌｍｎｏｐｑｒｓｔｕｖｗｘｙｚ"
         "，．")
_TABLE = str.maketrans(_ASCII, _FULL)


def to_fullwidth(text: str) -> str:
    """半角英数字を全角へ。カンマ・ピリオドは数字に挟まれたときだけ移す。"""
    if not text:
        return text
    # 先に数字の桁区切りだけ全角化する
    text = re.sub(r"(?<=\d)([,.])(?=\d)",
                  lambda m: "，" if m.group(1) == "," else "．", text)
    # 残りの英数字を全角へ（カンマ・ピリオドは対象外）
    out = []
    for ch in text:
        out.append(ch if ch in ",." else ch.translate(_TABLE))
    return "".join(out)


def ascii_left(text: str) -> list[str]:
    """まだ残っている半角英数字。空リストなら安全。"""
    return re.findall(r"[A-Za-z0-9]+", text or "")
```

使うときは変換して、残っていないことを表明する。

```python
body = to_fullwidth(body)
assert not ascii_left(body), ascii_left(body)
```

素朴に `str.maketrans` で全部変換しなかったのには理由がある。

**カンマとピリオドを一律に全角化すると、文末の句点まで巻き込む。** `そこが分かれ目です.` の `.` が `．` になると、日本語としては読みにくい。一方で `5,740` の `,` は全角にしないと落ちる。だから「**数字に挟まれているときだけ**」という条件を先に適用し、残りの `,` `.` は触らないようにした。

こういう変換は「弾きすぎ」の方向に壊れやすい。テストは両方向を固定した。落ちた実例で欠落が起きないことを見るだけでなく、**壊してはいけない入力が素通りすること**も見る。

```python
print("■ 実際に落ちた本文")
out = to_fullwidth("SIMロックだけ先に確認。410円が残り14回で5,740円、合計141,340円")
t("半角が1文字も残らない", ascii_left(out), [])
t("桁区切りのカンマが全角になる", "５，７４０" in out, True)
t("千の位も全角", "１４１，３４０" in out, True)

print("■ 通すべき（壊さない）")
t("日本語だけの文はそのまま",
  to_fullwidth("エリアマップで生活圏を見ておくと安心です。"),
  "エリアマップで生活圏を見ておくと安心です。")
t("文末の句点は全角ピリオドにしない",
  to_fullwidth("そこが分かれ目です。"), "そこが分かれ目です。")
t("読点はそのまま", to_fullwidth("まず、確認します。"), "まず、確認します。")
t("記号や絵文字は触らない", to_fullwidth("①②③🙏"), "①②③🙏")
```

そして**適用範囲を絞る**。落ちるのはブラウザの `type` だけなので、API 経由の投稿には変換をかけない。全角に寄せた本文は読みやすさで一段落ちるから、必要な経路にだけ通す。この線引きをモジュールの docstring に書いておかないと、後から全経路に配線されて本文が全部全角になる。

## ついでに踏んだ、同じ形の罠

同じエディタで、書き込み系のアクションが「成功を返すのに効いていない」ケースを他にも2つ踏んだ。

**下書きが消せない。** 入力をやり直そうとして `document.execCommand('delete')` を呼んでも消えない。クリックしてフォーカスを当ててから `Ctrl+A` → `Delete` でも消えない。**追記されるだけ**なので、リトライのたびに本文が二重三重に伸びていく。結局、確実なのはページの再読み込みだった。

**送信ボタンが押せない。** 要素検索で送信ボタンの参照を取ってクリックしても不発。`Ctrl+Enter` も不発。どちらも例外は出ず、下書きだけが残る。スクリーンショットを撮って**座標でクリック**したときだけ送信された。

3つとも症状が違うが、形は同じだ。**「操作は受理されたが、状態は変わっていない」** ——そしてどれもエラーを出さない。

## 教訓

書き込みの成否を、書き込み側の戻り値で判定していた。それが根本の間違いだった。

- **入力 API は「投げた文字列がそのまま入る」ことを保証しない。** UI 自動化では、書き込みと反映の間に IME・composition・エディタ独自の入力ハンドラが挟まる。変換されるし、欠落する。
- **部分的な欠落は、全部の失敗より危険。** 全部消えていれば空欄で気づく。一部だけ消えると、それらしい出力が残って正常系の顔をする。今回は「自然な日本語」が残ったせいで、目視レビューを2回とも通過した。
- **検算は読み戻しで、完全一致で、差分の位置まで出す。** 長さの比較では12文字の欠落を見落とす。自分の投げた値ではなく、相手側の状態を読む。
- **原因を大きく括らない。** 「このエディタには送れない」で止めていたら、`type` 固有の症状だと分からず、全角で回避する道も見つからなかった。手動・API・自動化ツールの3経路で同じ入力を試すのが切り分けとして一番速かった。

自動化ツールを変えれば直る類の問題ではある。ただ、どのツールを使っていても「書いたつもりの値が入っていない」は起こりうるし、そのとき頼りになるのは**送信前に読み戻して突き合わせる数行**だけだった。入力欄に何かを打ち込んで送信するコードを書いているなら、そこに `assert typed == expected` を1つ足しておく価値はある。
