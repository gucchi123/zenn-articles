[16媒体に自動配信するコンテンツ基盤](https://zenn.dev/mameresearcher/articles/multi-channel-content-automation-architecture) の続きです。前回は「媒体ごとに設計を変える」という配信側の話でした。今回は運用に入ってから起きたことを書きます。

結論から言うと、**壊れるのは配信ロジックではありませんでした。** 事故はほぼ全部、次の2箇所で起きています。

1. **関門（gate）** — 送っていいかを判定する場所
2. **確認（verification）** — 送れたかを判定する場所

どちらも「本体の外側」で、テストが薄くなりがちなところです。しかも**壊れても例外が出ません**。静かに間違った答えを返し続けます。

![関門と確認は本体の外側で壊れる](/images/agent-media-ops-gates.png)

## 関門の壊れ方は「弾きすぎ」に偏る

外部の投稿に反応してよいかを判定する関門を持っています。この関門で出た誤検知は、実測した範囲では**全部「弾きすぎ」側**でした。

### 事例1: 文字集合を作ると言語判定が文字判定になる

日本語以外を弾くために簡体字の文字集合を作って照合していました。その集合に `点` `双` `没` を入れていた。

これらは簡体字でもありますが、**同時に普通の日本語です**。結果、何の問題もない日本語が弾かれました。丸一日ぶん候補が空になって初めて気づいています。

### 事例2: 語の存在は、その語に対する立場を教えてくれない

商用色の強い相手を避けるため、本文に「アフィリエイト」があれば除外する規則を置きました。

ところが**アフィリエイトをやっていない人**が「私はアフィリエイトはやっていません」と書いている投稿も、同じ規則で落ちます。

これは気づいて記事にもしました。**それでもコードは直っていませんでした。** 数日後にテストを書いて初めて発覚しています。文章にした時点で直した気になっていた。

```python
# ❌ 裸の語で弾く
r"アフィリエイト"

# ✅ 自己申告の宣伝だけを狙って絞る
r"アフィリ(?:エイト)?(?:リンク|報酬|収益|案件|で稼)"
```

### 効いたのは「弾いてはいけない例」のテスト

関門のテストは、**弾くべき例だけ書くと必ず穴が開きます**。出力が減るだけなので、通しすぎと違って誰も気づかない。

```python
CASES = [
    # 弾くべきもの
    (False, "紹介はこちら r10.to/xxxxx スマホ代 悩んでる人どうぞ", "紹介リンク付き=同業"),

    # 🔴 弾いてはいけないもの（こちらを書かないと穴が開く）
    (True, "アフィリエイトはやってないんですが、スマホ代が高くて乗り換えを考えてます",
     "語はあるが本人はやっていない"),
    (True, "要点は配分で、双方の負担が没にならないよう点検した",
     "点・双・没 は日本語。誤検知しないこと"),
]
```

閾値を上げるという判断は、精度を上げる判断ではありません。**どちら側の誤りを許容するかを選ぶ判断**です。

## 判定の材料は「語」より「ドメイン」が強い

同業を避けたいという要件があります。語で判定しようとして、上のように何度も失敗しました。

決定的だったのは**リンク先のドメイン**です。

```python
ASP_DOMAIN_RE = re.compile(
    r"(trafficgate\.net|accesstrade\.net|valuecommerce\.com|a8\.net|"
    r"af\.moshimo\.com|rentracks\.jp|linksynergy\.com|felmat\.net)", re.I)
```

アフィリエイトASPのドメインは**一般ユーザーが書くことがありません**。「アフィリエイト」という語と違って、立場が一意に決まります。

実測で、候補3件が全部同業だったのに関門を素通りしたことがありました。3件とも本文にもタイトルにも宣伝語がなく、**証拠は説明文のリンクだけ**でした。

判定材料を探すときは、「その特徴を持つ人が他にいないか」を先に考えるほうが早いです。

## 確認の壊れ方は「不在で判定した」に集中する

もう一方の事故は全部これでした。**あるべきものが無いことを根拠にした**判定です。

### エラーは失敗の証拠にならない

- Facebook の投稿で `Network request timed out` が赤字で出た → **投稿は成功していた**。再送していたら重複投稿
- Pinterest が `HTTP 504 upstream request timeout` を返した → **ピンは作成されていた**
- Medium のログに `published: false` と記録された → **実際には公開されていた**

3件とも、エラーを見て再実行していたら重複を作っていました。

### 「その文字が無い」は「問題なし」ではない

ログイン状態を「`ログイン` という文字が無ければログイン済み」と判定するコードを書きました。そのサイトのボタン表記は `Log in` でした。**未ログインでも条件を満たします。**

同じ日にもう一度やっています。今度は「アバターの要素があるか」で見ようとして、クラス名が変わっていて未ログイン判定。実際はログインできていました。

```javascript
// ❌ 不在で判定する
loggedIn: !/ログイン/.test(document.body.innerText)

// ✅ ログイン後にしか存在しないものの存在で判定する
loggedIn: !!document.querySelector('[data-testid="SideNav_AccountSwitcher_Button"]')
          && !document.querySelector('input[type="password"]')
```

### 測る道具のほうが壊れていることがある

読み上げ音声の検証に文字起こしモデルを使っています。ある日、いくつかの語が誤読されていると判定して発音辞書に7語追加しました。

**実際には音声のほうが正しく、文字起こし側が聞き取りを間違えていました。** 精度の高いモデルで取り直したら全部一致しています。

**測られる側を直す前に、測る側を疑う。** 同じ型の誤診をその日だけで4回やって、ようやく手順にしました。

## 手順にしたこと: 対照を取る

上の失敗に共通する対処は1つです。**同じ観測を、正常と分かっている対象にも当てる。**

コメント可否の判定を書いたとき、候補3件が全部「不可」と出ました。内容の問題だと思いかけたのですが、**以前コメントできたブログでも「不可」**と出て、初めて判定側の不具合だと分かりました。

```javascript
// ❌ 一気に最下部へ飛ばすと、遅延描画のコメント欄が起きない
await page.evaluate(() => window.scrollTo(0, document.body.scrollHeight));

// ✅ 刻んで降りる
for (let i = 0; i < 25; i++) {
  await page.evaluate(() => window.scrollBy(0, 700));
  await page.waitForTimeout(300);
}
```

対照が無ければ、私はそのまま「このブログはコメント無効だ」と記録していました。

## 送信前に、下書きが残っていないか見る

エディタを持つ媒体で、`--dry-run` の下書きが**リロードしても保持される**ものがあります。

dry-run で内容を確認し、そのまま本番を実行したところ、**下書きの上に追記されて公開されました**。493字のはずが894字、同じ文章が二重に並んで末尾で切れた状態です。

「下書きはリロードしても保持される」という**自分で書いた仕様メモが、そのまま罠になりました**。

対処は2つ入れました。

```javascript
// 1. 打つ前に必ず空にする（空のCodeMirrorはプレースホルダを返すので誤認しない）
const PLACEHOLDER = /^(記事についてコメントする|内容を編集)$/;
for (let i = 0; i < 6; i++) {
  await page.keyboard.press('Control+a');
  await page.keyboard.press('Delete');
  const rest = await page.evaluate(() => document.querySelector('.cm-content')?.innerText ?? '');
  if (!rest.trim() || PLACEHOLDER.test(rest.trim())) break;
}

// 2. 入力後に長さを検算する
if (typed.length > TEXT.length * 1.15) {
  console.error('下書きと混ざっている。送信しない');
  process.exit(8);
}
```

## 環境そのものが原因のことがある

ブラウザ操作が丸一日動かず、拡張の不具合・サイト権限・セレクタと順に疑いました。全部外れです。

**Windows がロック画面でした。**

```
LogonUI プロセス     あり = ロック中
前面のウィンドウ      Windows Default Lock Screen
```

ロック中の Windows はデスクトップを描画しないので、ブラウザの全タブが `visibilityState: hidden` になります。SPA が描画されず、本文が0文字になり、要素が見つからない。

分かれ目は**描画が要るかどうか**でした。

- Playwright / CDP … **動く**（DOM を直接操作する。描画不要）
- API … **動く**
- ブラウザ拡張経由 … **動かない**（実レンダリングとスクリプト注入を使う）

同じ日に、Playwright と API を使う媒体は全部通り、拡張を使う媒体だけが止まっています。症状は正しく報告できていましたが、**原因の切り分けが遅すぎました**。

以後、ブラウザ操作が理由不明で止まったら、セレクタより先に `Get-Process LogonUI` を見ています。

## まとめ

1年運用して、コードの本体を直した回数より**関門と確認を直した回数のほうが多い**です。

- **関門は「弾いてはいけない例」を対でテストに書く。** 弾きすぎはエラーとして表面化せず、出力が減るだけで正常に見える
- **判定材料は「語」より「ドメイン」。** 立場が一意に決まるものを探す
- **確認は不在ではなく、成功時にしか出ないものの存在で書く**
- **エラーを見たら、再送する前に成立確認をする**
- **同じ観測を正常な対象にも当てる。** 対照が無いと、判定側の不具合を対象の性質だと読み違える
- **気づいた時点でテストに落とす。** 文章にしただけでは直らない

最後のが一番効きました。文章は自分を安心させますが、テストは落ちてくれます。
