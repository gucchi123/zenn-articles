LINE 公式アカウントで、録画を疑似ライブとして流すオートウェビナーを作りました。10分の解説動画に、台本どおりのコメントが流れ、途中で申し込みボタンが出る形式です。

動画の作り方でひとつ判断があって、そこが効いたので書きます。**Remotion を使わず、1ターン＝1枚の静止画にした**という話です。

結論だけ先に書くと、こうなりました。

- 78ターンの会話劇が **9分48秒**、1920x1080 で **25MB**
- 映像と音声のズレは**構造的にゼロ**
- 1080p の HLS でも実効 **660kbps** 程度

![1ターン1枚の静止画にすると同期が構造的に保証される](/images/auto-webinar-static-frames.png)

## なぜ動きをつけないのか

最初は Remotion で作ろうとしていました。React で動画を書けるので、字幕のフェードやキャラの動きを入れられます。

やめた理由は単純で、**凝ると完成しないから**です。

会話劇の解説動画で視聴者が見ているのは、話している内容とテロップです。キャラが動くかどうかは本質ではない。一方で、動きを入れると尺の管理・音声との同期・レンダリング時間が全部増えます。

もうひとつ、実務的な理由があります。Remotion は**原寸の PNG を背景に置くと落ちることがある**ので、素材側の調整も要ります。動画1本作るために解決すべきことが増えていく。

「終わらせやすい作りを選ぶ」ほうを取りました。

## 1ターン1枚にすると同期が構造的に保証される

やり方はこれだけです。

1. 台本を話者ごとのターンに割る
2. ターンごとに TTS で音声を作る
3. ターンごとにフレーム PNG を1枚描く
4. **各フレームの表示秒数 = そのターンの音声長 + 間**

音声と映像が同じ数字から出てくるので、**ズレる余地がありません**。フレーム側で秒数を計算する必要も、後から合わせ込む工程もない。

```python
def add(png, dur):
    lines.append(f"file '{Path(png).as_posix()}'")
    lines.append(f"duration {dur:.3f}")

add(BUILD / "title.png", TITLE_SEC)
for i in range(len(turns)):
    gap = GAP_SECTION if (i + 1) in SECTION_STARTS else GAP
    add(FRAMES / f"f{i:03d}.png", wav_seconds(vpath(turns, i)) + gap)
add(BUILD / "end.png", END_SEC)

# 🔴 concat demuxer の作法: 最後のファイルは duration 無しでもう一度書く
lines.append(f"file '{(BUILD / 'end.png').as_posix()}'")
```

音声側も同じ間（ま）で繋ぎます。`wave` だけで足ります。

```python
sil = lambda sec: b"\x00" * int(rate * sec) * ch * sw

with wave.open(str(out), "wb") as w:
    w.setparams(params)
    w.writeframes(sil(TITLE_SEC))
    for i in range(len(turns)):
        with wave.open(str(vpath(turns, i))) as src:
            w.writeframes(src.readframes(src.getnframes()))
        gap = GAP_SECTION if (i + 1) in SECTION_STARTS else GAP
        w.writeframes(sil(gap))
    w.writeframes(sil(END_SEC))
```

セクションの切れ目だけ間を長くしています（0.34秒 → 0.85秒）。これだけで話の区切りが耳で分かります。

## フレームは Pillow で描く

1枚あたりに置くもの:

- ヘッダー（タイトル・ブランド・現在のセクション）
- キャラ2体。**話している側を明るく、待機側を褪せさせる**
- テロップ（そのターンの台詞。長さに応じて自動でフォント縮小）
- 区切りの結論を出す強調バンド（数箇所だけ）

待機側の処理でひとつ引っかかりました。**暗い色のキャラを暗い背景の上で「沈める」と、消えてしまいます。**

```python
def dim(im, alpha=0.52):
    r, g, b, a = im.split()
    gray = Image.merge("RGB", (r, g, b)).convert("L").convert("RGB")
    flat = Image.blend(Image.merge("RGB", (r, g, b)), gray, 0.65)
    # 🔴 暗い側でなく明るい側へ寄せて「褪せさせる」。
    #    背景色へ寄せると、濃紺のキャラが背景に溶けて見えなくなる
    flat = Image.blend(flat, Image.new("RGB", im.size, (126, 146, 172)), 0.48)
    return Image.merge("RGBA", (*flat.split(), a.point(lambda v: int(v * alpha))))
```

もうひとつ、地味に時間を取られた点。

**Pillow の `rounded_rectangle` は `fill` のアルファを無視して不透明に描きます。** 半透明の箱を描いたつもりが真っ白になり、上に載せた白文字が読めませんでした。合成後の実色を直接指定するのが確実です。

## 声は基本周波数を測って選ぶ

話者2人の声は、TTS の VoiceDesign で候補を作って選びました。選定を耳だけでやると危ないので、**基本周波数を実測して**決めています。

- 候補1（低め男性）… **107Hz**
- 候補2（中性の講師風）… 209Hz
- 候補3（柔らかめ男性）… 134Hz

相方はすでに決まっていて **250Hz**。候補2だと差が **41Hz** しかなく、聞いていて混同しました。候補1なら **143Hz** 離れているので、音だけで話者が分かります。

参照音声方式で再生成しても 110Hz を維持していたので、量産しても声が分岐しないことも確認しています。

## 踏んだ罠

### PATH の ffmpeg に libx264 が無い

```
Unknown encoder 'libx264'
```

`ffmpeg -encoders | grep 264` を見ると `h264_nvenc` `h264_amf` `libopenh264` などが並ぶので、一見あるように見えます。**ハードウェア系しか無い最小ビルドでした。**

フルビルドを絶対パスで名指しするようにしています。

### Windows の ffmpeg は master.m3u8 にバックスラッシュを書く

HLS に変換したら、マスタープレイリストがこうなっていました。

```
#EXT-X-STREAM-INF:BANDWIDTH=957045,RESOLUTION=1920x1080
0\index.m3u8
```

`0\index.m3u8` はブラウザからもオブジェクトストレージのキーとしても解決できません。変換後に必ず `/` へ直します。

```python
re.sub(r"^(\d+)\\(index\.m3u8)$", r"\1/\2", s, flags=re.M)
```

### 発音の検証で、測る側が壊れていた

合成した音声を文字起こしして台本と突き合わせています。ある日いくつかの語が誤読と判定され、発音辞書に7語追加しました。

**実際には音声のほうが正しく、文字起こしモデルの精度が足りていませんでした。** 大きいモデルで取り直したら全部一致しています。

音声の検証は、小さいチェックポイントを使わないほうがいい。**測られる側を直す前に、測る側を疑う。**

## 🔴 いちばん危なかったこと: CTAが一度も出ない設計になっていた

技術的な話ではないのですが、これが本番だったら一番損害が大きかったので書いておきます。

動画を組み終えて設定と突き合わせたとき、こうなっていました。

- CTA（申し込みボタン）の表示位置 … **600秒**
- 動画の長さ … **588秒**

**成果地点が一度も現れません。** 配信して、最後まで見てもらって、それでもボタンは出ない。

原因は単純で、台本を書いた時点では21分（1,260秒）の構成だったからです。中盤の600秒に置くのは筋が通っていました。ところが音声を作って組み立てたら9分48秒にしかならなかった。

**問題は尺が短くなったこと自体ではなく、短くなったあとで秒数を採り直さなかったこと**です。台本・動画・設定が別々に置かれていて、どれかが変わったときに他が追随する仕組みがありませんでした。

対処として、組み立てスクリプトが**実尺のタイムラインを吐く**ようにしました。

```python
t, marks = TITLE_SEC, {}
for i in range(len(turns)):
    if i in SECTION_STARTS:
        marks[section_for(i)] = round(t, 1)
    if i == CTA_TURN:
        marks["__CTA__"] = round(t, 1)
    t += secs[i + 1]
marks["__END__"] = round(t + END_SEC, 1)
(BUILD / "timing.json").write_text(json.dumps(marks, ensure_ascii=False, indent=2))
```

```json
{
  "今日の問い": 4.0,
  "AIが数字を間違える仕組み": 63.6,
  "ご案内": 364.7,
  "__CTA__": 364.7,
  "__END__": 587.6
}
```

設定側の秒数は、この JSON から採ります。**想定尺ではなく実物から。**

## 静止画にした副作用: 圧縮が異常に効く

HLS を 1080p / 720p / 480p の3本で作りました。1080p のビットレート目標を 4,200kbps にしていたのですが、実際に出たマスタープレイリストがこれです。

```
#EXT-X-STREAM-INF:BANDWIDTH=957045,AVERAGE-BANDWIDTH=665043,RESOLUTION=1920x1080
```

**平均 665kbps。** 目標の1/6です。静止画が数秒ずつ続くので、x264 が使うビットを持て余しています。

294セグメント・3画質の合計で 112MB。配信コストの観点でもかなり軽い。テロップの文字も潰れていないことを、変換後のセグメントからフレームを抜いて確認しています。

## まとめ

- **会話劇に動きは要らない。** 1ターン1枚の静止画にすると、映像と音声のズレが構造的に消える
- **声は測って選ぶ。** 基本周波数で 143Hz 離れていれば、音だけで話者が分かる
- **実物ができたら、実物から数字を採り直す。** 想定尺のまま設定を置くと、成果地点が存在しない動画ができる
- 環境側の罠（libx264 の無いビルド / Windows の `\` / Pillow のアルファ無視）は、いずれも**エラーが出ないか、出ても原因が読めない**形で来る

凝った映像より、最後まで行ける作りを選ぶ。今回いちばん効いた判断はそこでした。
