個人の自動化プロジェクトで、Windows のタスクスケジューラに 170 本ほどの定期タスクを載せている。各 SNS の数字を取ってくる集計タスクもその一部で、夜の 21:05〜21:50 に数分ずつずらして並べてある。一部には RandomDelay も付けてある。

ある晩、その 10 本が **21:50:50 の同じ秒に**一斉に起動していた。

## 症状

タスクの「前回の実行時刻」を並べると、こうなっていた。

| タスク | 予定時刻 | RandomDelay | 前回の実行時刻 |
|---|---|---|---|
| YouTube | 21:05 | 20分 | 21:50:50 |
| TikTok | 21:15 | なし | 21:50:50 |
| Threads | 21:20 | なし | 21:50:50 |
| Instagram | 21:25 | 20分 | 21:50:50 |
| Facebook | 21:26 | なし | 21:50:50 |
| BlueSky | 21:27 | なし | 21:50:50 |
| Mastodon | 21:28 | なし | 21:50:50 |
| Livedoor | 21:35 | 8分 | 21:50:50 |
| note | 21:40 | なし | 21:50:50 |
| Tips | 21:50 | なし | 21:50:50 |

この晩、PC は 20:54〜21:50 にスタンバイしていた。10 本の予定時刻は、すべてその中に入っている。

![予定時刻は21:05〜21:50に分散していたが、スタンバイ中に過ぎた10本が復帰後の同じ秒に起動した。対策として実行ラッパーに同時実行枠を2つ設けた](/images/standby-resume-task-stampede.png)

## 原因

10 本とも「スケジュールされた開始時刻にタスクを開始できなかった場合、すぐにタスクを実行する」(`StartWhenAvailable`) が有効になっている。スタンバイ中に予定時刻を過ぎたタスクは、復帰したところでまとめて起動される。

予定時刻を数分ずつずらすのも、RandomDelay で揺らすのも、効くのは**予定時刻そのもの**に対してだ。ずらした先の時刻がまるごとスタンバイの中に入っていれば、復帰の瞬間には全部が「過ぎた分」として同じ扱いになる。分散はそこで消える。

以前、同じ構造の問題を一度踏んでいる。重い手作業で PC が塞がっている間にタスクが積まれ、空いた瞬間に同時に起動して、実行時間の上限 (30 分以下のものが多かった) を超えて強制終了 (`0x41306` = 267014) される、というものだった。そのときは、落ちたタスクに RandomDelay を 20〜45 分付け、`MultipleInstances` を `IgnoreNew` にし、上限を現実的な値に上げた。

ただ、今回のようにスタンバイの時間が予定時刻の範囲を覆ってしまうと、RandomDelay では防げない。**スケジュール側でできることには限りがあり、起動した後に並べる仕組みが要る。**

## 対処: 実行ラッパーに「同時実行枠」を足す

集計タスクの多くは、もともと共通の実行ラッパー (`run_logged.py`) 経由で起動している。ネットワークの回復を待ってから本体を起動し、接続エラーのときだけ 1 回再試行するためのものだ。ここに 2 つの引数を足した。

```text
run_logged.py --lock metrics --parallel 2 --timeout-min 27 <script.py> ...
```

同じ `--lock` 名のタスクは、同時に `--parallel` 本までしか本体を走らせない。

```python
def acquire_slot(name: str, parallel: int, max_wait_sec: int, log):
    """同じグループの同時実行を parallel 本までにする（空きが出るまで待つ）。"""
    d = Path(os.environ.get("TEMP", ".")) / "run_logged_locks"
    d.mkdir(exist_ok=True)
    t0 = time.time()
    while True:
        for i in range(parallel):
            f = d / f"{name}_{i}.lock"
            try:
                fd = os.open(str(f), os.O_CREAT | os.O_EXCL | os.O_WRONLY)
                os.write(fd, str(os.getpid()).encode()); os.close(fd)
                return f
            except FileExistsError:
                try:
                    pid = int(f.read_text().strip() or 0)
                except Exception:
                    pid = 0
                if pid and not _pid_alive(pid):
                    f.unlink(missing_ok=True)   # 落ちたプロセスの残骸
        if time.time() - t0 > max_wait_sec:
            log(f"[wrapper] {name} の空き待ちが {max_wait_sec}s を超えたので待たずに実行")
            return None
        time.sleep(20)
```

本体が終わったら、取った枠のファイルを消す。

### 決めたこと

**枠は「ファイルを排他的に作れたか」で取る。** `O_CREAT | O_EXCL` は、ファイルが既にあれば失敗する。存在の確認と作成が 1 回の呼び出しで済むので、同じ秒に 10 本が来ても、枠を取れるのは 1 つの枠につき 1 本だけになる。「無ければ作る」を 2 手に分けると、その間に別のタスクが割り込む。

**中身には PID を書き、死んでいたら残骸として消す。** タスクスケジューラが上限で強制終了すると、ラッパーごと止まるので、枠のファイルを消す処理まで届かない。放っておくと枠が 1 つずつ減っていき、最後は全員が待ち続けることになる。次に来たタスクが PID を見て、そのプロセスが居なければ消して取り直す。

生死の判定ができなかったときは「生きている」とみなす。他のタスクが使っている枠を誤って奪うより、少し待つほうが害が小さい。

**待つのは持ち時間の半分まで。** 待っている間もタスクの実行時間は減っていく。待ちすぎて本体を走らせる前に上限で殺されたら、待った意味が無い。半分を超えたら枠を取らずに実行する。順番待ちは「なるべく重ならないようにする」ためのもので、集計が 1 日抜けるほうが困る。

**グループは用途で分ける。** 今は `metrics` の 1 グループに、ラッパー経由で動いている集計タスク 6 本を入れ、同時実行を 2 本にした。重さの近いものを同じグループに入れる。全タスクを 1 つの枠に入れると、軽いタスクが重いタスクの後ろで待たされる。

## 残っていること

- 10 本のうち 4 本は、まだこのラッパーを通っていない (別の起動方法のまま)。これらは枠を取らないので、復帰時には 2 本 + 4 本が同時に走りうる
- PID は再利用される。死んだプロセスの PID を別のプロセスが使っていると、残骸を「生きている」と見誤る。その場合も、待ち時間の上限で抜けるので止まりはしない
- 効果の確認は次のスタンバイ復帰を待っている。見るのはログの `[wrapper] slot metrics: metrics_0.lock` の並びと、各タスクの終了コード

## 教訓

- **予定時刻をずらすのは、予定時刻の分散でしかない。** PC が止まっている間に過ぎた分は、復帰したときにまとめて出てくる。`StartWhenAvailable` を有効にしているなら、その一斉起動は必ず起きる前提で考える
- **起動時刻で防げないものは、起動した後に並べる。** 共通の実行ラッパーがあれば、そこに枠を足すだけで済む
- **ロックは「取れなかったとき」と「返せなかったとき」まで決める。** 待つ上限と、残骸の掃除が無いロックは、いずれ全員を止める
