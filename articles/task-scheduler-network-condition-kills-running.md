個人の自動化プロジェクトで、Windows のタスクスケジューラに 180 本あまりの定期タスクを載せている。SNS への投稿、API からの数字の取得、トークンの更新などで、ほぼ全部がネットワークを使う。

ノート PC なので、スリープ明けに「起きた瞬間はまだ Wi-Fi がつながっておらず、名前解決に失敗して落ちる」タスクが毎朝いくつか出ていた。そこで、ネットワークを使う 184 本に、タスクの条件「ネットワーク接続が使用可能な場合のみ開始する」(`RunOnlyIfNetworkAvailable`) を一括で入れた。

翌朝、それが原因で 8 本が同時に死んだ。

## 症状

翌朝のタスク履歴はこうだった。

- 08:30 スリープから復帰。予定時刻を過ぎていたタスク 8 本が起動する
- 08:31:43 Wi-Fi ドライバが再接続する
- **同じ瞬間に、実行中だった 8 本が全部終了**。戻り値は `2147943467`

`2147943467` を 16 進にすると `0x8007042B`。下位 16 ビットの `0x042B` (1067) は `ERROR_PROCESS_ABORTED` で、「プロセスが外から止められた」という意味になる。スクリプト自身が例外で落ちたのではない。

```powershell
PS> '{0:X}' -f 2147943467
8007042B
PS> [ComponentModel.Win32Exception]::new(0x42B).Message
The process terminated unexpectedly
```

同じ瞬間に、この条件を付けていないタスク (別のアプリが入れた更新チェックなど) は生き残っていた。違いは条件の有無だけだった。

## 原因

タスクスケジューラの「条件」(Conditions) は、**開始の条件であると同時に、続けるための条件**でもあった。

UI の文言は「開始する」なので、「つながっていなければ開始を待つ」設定だと読んでいた。実際には、実行中にネットワークが「使用不可」になると、その時点で実行中のタスクも止められる。スリープ明けの Wi-Fi は、一度つながったように見えてから、ドライバの再初期化や接続先の切り替えで一瞬切れることがある。その一瞬に当たったタスクが全部まとめて殺された。

期待と実際の差を並べるとこうなる。

| | 期待していた挙動 | 実際の挙動 |
|---|---|---|
| 予定時刻にネットワークが無い | つながるまで待ってから開始 | 開始しない (待つ) |
| 実行中にネットワークが一瞬切れる | (考えていなかった) | **実行中のプロセスを止める** |

後者が怖いのは、止まるタイミングを選べないことだ。投稿 API を呼んだ直後、ファイルを書き換えている途中、アップロードの途中でも容赦なく止まる。「投稿は成功したが台帳に記録する前に死んだ」が起きると、次の実行で二重投稿になる。

さらに、効果を確かめずに 184 本へ一括で入れたので、被害も一括になった。普段なら時間がずれて 1〜2 本で済むはずの失敗が、**同じ秒に 8 本**になった。

## 対処

### 1. 条件を元の値に戻す

変更前にタスク定義を XML でバックアップしていたので、**元から無効だったものだけ**を無効に戻した。最初から条件が有効だったタスク (ほかの人やアプリが意図して入れたもの) まで一律に外すと、それはそれで別の変更になってしまう。

```powershell
# 変更前に取った XML (Export-ScheduledTask の結果) を見て、元が無効だったものだけ戻す
$backup = "C:\path\to\task_backups\before_network"
Get-ChildItem $backup -Filter *.xml | ForEach-Object {
    [xml]$x = Get-Content $_.FullName -Raw -Encoding Unicode
    $orig = $x.Task.Settings.RunOnlyIfNetworkAvailable   # 要素が無ければ既定の false
    if ($orig -ne 'true') {
        $t = Get-ScheduledTask -TaskName $_.BaseName
        $t.Settings.RunOnlyIfNetworkAvailable = $false
        Set-ScheduledTask -InputObject $t | Out-Null
    }
}
```

バックアップ 186 件のうち、元から有効なものは残し、それ以外を戻した。

### 2. ネットワーク待ちはスクリプト側でやる

「起きた瞬間はまだつながっていない」問題そのものは残るので、待つのは**タスクの条件ではなく、実行ラッパーの中**でやる。ラッパーは開始前に一度だけ接続を確かめ、つながらなければ一定時間リトライし、本体が走り出した後はネットワークの状態で止めない。

```python
NET_HOSTS = [("www.google.com", 443), ("1.1.1.1", 443)]

def net_ok() -> bool:
    for host, port in NET_HOSTS:
        try:
            with socket.create_connection((host, port), timeout=5):
                return True
        except OSError:
            continue
    return False

def wait_net(log, max_sec: int) -> bool:
    t0 = time.time()
    if net_ok():
        return True
    log(f"[wrapper] 通信なし。最大{max_sec // 60}分待つ")
    while time.time() - t0 < max_sec:
        time.sleep(30)
        if net_ok():
            log(f"[wrapper] 通信回復 ({int(time.time() - t0)}秒後)")
            return True
    log("[wrapper] 通信が戻らないまま待ち時間切れ")
    return False
```

実行中の一瞬の切断は、各スクリプトの HTTP 呼び出しのリトライに任せる。プロセスごと殺されるのと違って、リトライならどこまで終わったかを本人が知っている。

### 3. スリープ明けの渋滞は別の手で

そもそもの動機だった「スリープ明けの一斉失敗」には、タスク設定ではなく、復帰イベントを見て数分待ってから取りこぼしたタスクを 1 本ずつ流す仕組みで当たることにした。暦のトリガーに付ける遅延 (Delay) は、スリープ中に過ぎた分の追い付き起動には効かないので、これも設定だけでは解決しない。

## 教訓

- **タスクの「条件」は継続の条件でもある。** 「ネットワーク接続時のみ」は「切れたら止める」を含む。電源 (「AC 電源の場合のみ」) やアイドル (「アイドル状態の場合のみ」) の条件にも、同じく「条件が外れたら止める」側の設定がある。条件を足すときは「実行中に条件が崩れたらどうなるか」を先に確かめる。
- **「待つ」はタスクの外ではなく中に書く。** 待ち方・待つ時間・あきらめ方を自分で決められるし、ログにも残る。OS の条件に任せると、止まったことが `0x8007042B` 一行でしか分からない。
- **一括変更は、数本で翌日の結果を見てから広げる。** 今回の失敗は設定の誤解そのものより、効果を確かめずに 184 本へ入れたことで被害が揃ったことの方が大きかった。バックアップを取ってあったので戻すのは 1 本のスクリプトで済んだ。一括で変えるなら、少なくとも「元の値」を機械的に戻せる形で残しておく。
- **戻り値は 16 進にして下位ビットを見る。** `2147943467` のままでは何も分からないが、`0x8007042B` → `0x42B` → `ERROR_PROCESS_ABORTED` まで崩すと、「自分のコードではなく外から止められた」と分かり、調べる場所が一気に絞れる。
