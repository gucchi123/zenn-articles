複数のSNSを横断して「こちらに来ている反応のうち、まだ返していないもの」を洗うスクリプトがある。冷たい相手に出ていくより、既に反応してくれた相手に返すほうが効くので、毎日の運用でこれを最初に回している。

今日それを実行したら、こう出た。

```
  楽モバ研究所: 未返信 0 件
```

終了コードは 0。stderr は空。「今日は返すものがないんだな」と読んで、次の作業に移りかけた。

実際には **5件たまっていた**。一番古いものは13日前だった。

## 何が起きていたか

スクリプトの構造はこうなっている。

```python
sys.stdout.reconfigure(encoding="utf-8")

def bluesky():
    print("\n=== BlueSky（通知） ===")
    ...

def threads():
    print("\n=== Threads（自分の投稿への返信） ===")
    ...

def youtube():
    ...
    print(f"  {name}: 未返信 {len(un)} 件")

bluesky()
threads()
youtube()
```

3つとも呼ばれている。`bluesky()` の1行目は `print` だ。それなのに、その見出しすら出ない。

最初は「関数が呼ばれていないのでは」と疑った。定義の重複がないか、後から名前を上書きされていないか、同期フォルダに競合コピーができて別のファイルが実行されていないか。どれも空振りだった。ソースを何度読んでも、`print` はそこにある。

切り分けのために、末尾の呼び出しを外して `bluesky()` だけを単独で呼んでみた。

```
=== BlueSky（通知） ===
  直近 47 件 / 内訳: {'like': 25, 'reply': 8, 'follow': 13, 'repost': 1}
  [4日前] @...
  [5日前] @...
```

**完璧に動く。** 5件ちゃんと出る。

ここでようやく見当がついて、`-u` を付けて元のまま実行した。

```
python -u inbound_audit.py
```

全部出た。

## 原因

![stdout のバッファリングで、先に出した結果だけが消える](/images/stdout-buffering-20260813.png)

Python は stdout がパイプに繋がっていると出力を貯め込む。端末に直接出しているときは行ごとに流すが、パイプだと 8KB ほど貯めてからまとめて書く。

そして `youtube()` の中で Google の認証ライブラリを読んでいる。この過程で、貯め込まれていた分が**書き出されないまま捨てられた**。

結果として、

- `bluesky()` と `threads()` の出力 → 貯め込まれ、消えた
- `youtube()` の出力 → 消えた後に書かれたので、生き残った

「1行だけ出る」という中途半端な壊れ方は、これで説明がつく。

修正は1行だった。

```python
sys.stdout.reconfigure(encoding="utf-8", line_buffering=True)
```

## 気持ち悪かったのは、失敗に見えなかったこと

この手の不具合で厄介なのは、出力が**もっともらしい**ことだ。

```
  楽モバ研究所: 未返信 0 件
```

これは正常系の表示そのものだ。エラーメッセージでもないし、`—` や `N/A` のような「取れませんでした」の顔もしていない。**0 は、実際に0件だったときと同じ見た目をしている。**

似た構造の不具合を、同じ週に別の場所でも踏んでいた。ファイルの読み込みに失敗したとき空のリストを返す実装があって、集計表に「投稿数 0」と出た。実際には201件あった。

```python
def load_posts(path):
    try:
        return json.loads(path.read_text(encoding="utf-8"))["posts"]
    except Exception:
        return []        # ← ここ
```

`return []` も `0 件` も、書いた本人には「安全なフォールバック」に見える。落ちないから。でも読む側からすると、**「無い」と「読めなかった」の区別がつかない形で報告されている**。

フォールバック値が、正常な観測値と同じ型・同じ見た目になっていないか。`except: return []` / `return 0` / `return ""` は、たいていこの罠を作る。

後者は、リトライしてなお読めなければ例外を上げるように変えた。黙って 0 を出すより、落ちて気づくほうがましだった。

## 教訓

**「動いた」と「結果が届いた」は別**だと、頭では分かっていたつもりだった。関数が呼ばれているかを確かめる検査は入れていたし、終了コードも見ていた。

今回はその一段外側だった。関数は呼ばれ、正しく計算し、`print` も実行された。**それでも結果は届かなかった。**

パイプに繋いで使うスクリプトで、途中に外部ライブラリの初期化が挟まるなら、`line_buffering=True` を先に入れておく。1行のコストで、こういう見つけにくい消え方を丸ごと防げる。

そしてもうひとつ。**単体で動かして直ったら、必ず元の呼ばれ方に戻して確かめる。** 今回は関数単体では完全に正常だった。そこで満足していたら、原因は永久に見つからなかった。
