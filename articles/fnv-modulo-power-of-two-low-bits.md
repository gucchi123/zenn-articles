個人の自動化プロジェクトで、リダイレクト用の小さな Worker を動かしている。今回、そこに「1つの入口URLから来た人を、8つの飛び先に均等に振り分ける」機能を足した。入口のURLは紙に印刷した QR コードに入る。印刷したあとは URL を変えられないので、振り分けはサーバー側でやることにした。

条件は2つ。

- 8つの飛び先にほぼ均等に散ること
- **同じ端末は何度開いても同じ飛び先に行くこと**(再訪のたびに行き先が変わると、記録上の帰属が後から上書きされてしまう)

2つ目があるので乱数は使えない。そこで「IP + User-Agent をハッシュして、8で割った余り」にした。よくある書き方で、本番にも出した。

**出したあとで測ると、8つの飛び先のうち3つに1件も来ていなかった。**

![FNV-1a を % 8 で割ると、各文字の下位3ビットしか見ていない](/images/fnv-modulo-low-bits.png)
*剰余の前に撹拌を1段挟むだけで、偏りが消える*

## 症状

最初に書いたコードはこれ。FNV-1a は短くて速く、Worker の中で依存なしに書けるので選んだ。

```ts
const ARMS = ["A", "B", "C", "D", "E", "F", "G", "H"] as const;

function fnv1a(s: string): number {
  let h = 2166136261;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 16777619);
  }
  return h;
}

function pickArm(ip: string, ua: string) {
  return ARMS[(fnv1a(ip + "|" + ua) >>> 0) % ARMS.length];
}
```

リリース前のテストでは、ランダムな IPv4 を8万件生成して流した。結果はこう。

```
random IPv4   10002, 9954, 10165, 10118, 9894, 9908, 10066, 9893   hit 8/8
```

偏りは±2%以内。問題なさそうに見えた。

リリース後、本番の Worker に「記録しないテスト用リクエスト」を **同じIP・User-Agent が少しずつ違う24本** で流した。8つの飛び先のうち当たったのは **4つだけ**。残り4つのうち3つは0件だった。

あとから同じ現象を手元で再現した。IPを固定し、User-Agent のバージョン番号の2桁だけを `{0, 1, 8, 9}` の組み合わせで変えた16本を流す。

```ts
const ua = (v: string) =>
  `Mozilla/5.0 (Linux; Android 14) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/${v} Mobile Safari/537.36`;

const inputs: string[] = [];
for (const a of "0189") for (const b of "0189")
  inputs.push("203.0.113.7|" + ua(`13${a}.0.${b}.0`));
```

```
raw % 8    8, 0, 0, 0, 0, 8, 0, 0   hit 2/8
```

16本が、きれいに2つの飛び先に8本ずつ集まった。偶然でこうはならない。

## 原因: FNV-1a の下位 k ビットは、各文字の下位 k ビットだけで決まる

FNV-1a の1ステップは「xor して、奇数を掛ける」だけ。

```
h ^= c
h  = h × 16777619  (mod 2^32)
```

このどちらも、**上位ビットの違いを下位ビットへ伝えない**。

- xor はビットごとの演算なので、ビット i の結果はビット i の入力だけで決まる
- 掛け算(mod 2^32)の結果の下位 k ビットは、掛ける数どうしの下位 k ビットだけで決まる。繰り上がりは下から上にしか伝わらない

したがって `fnv1a(s) % 8`(= 下位3ビット)は、**入力の各文字の下位3ビットだけで決まる**。上位ビットの違いは、どれだけあっても結果に出てこない。

数字で見るとわかりやすい。

```
'0' = 0x30 = 0011 0000
'8' = 0x38 = 0011 1000   ← 下位3ビットは '0' と同じ 000
'1' = 0x31 = 0011 0001
'9' = 0x39 = 0011 1001   ← 下位3ビットは '1' と同じ 001
```

`Chrome/130` と `Chrome/138` は、`% 8` から見ると同じ文字列になる。さっきの16本は、`% 8` から見ると実質4種類しかなかった。そのうえ4種類のうち2組がさらに同じ飛び先になって、結果は2つに集まった。

念のため、この性質を機械的に確かめた。ランダムな20文字の文字列 a を作り、各文字の下位3ビットはそのまま、上位ビットだけをランダムに変えた b を作って、`fnv1a(a) % 8` と `fnv1a(b) % 8` を比べる。これを10万組やって、**不一致は0件** だった。

```js
let bad = 0;
for (let t = 0; t < 100000; t++) {
  let a = "", b = "";
  for (let i = 0; i < 20; i++) {
    const c = 32 + Math.floor(Math.random() * 90);
    a += String.fromCharCode(c);
    b += String.fromCharCode((c & 7) | (Math.floor(Math.random() * 16) << 3));
  }
  if ((fnv1a(a) >>> 0) % 8 !== (fnv1a(b) >>> 0) % 8) bad++;
}
console.log(bad); // 0
```

### なぜテストで見逃したか

ランダムな IPv4 で測った試験では、入力の **下位ビット自体がランダム** だった。ランダムな下位ビットを入れれば、出力の下位ビットもランダムに見える。どれほど弱いハッシュでも、入力が十分ばらけていれば均等に見える。

一方、本番で起きるのは逆の条件だ。

- モバイル回線はキャリアの NAT で、**多くの人が同じIPを共有する**
- 同じ機種・同じブラウザの User-Agent は、**バージョン番号の数文字しか違わない**

つまり「似た入力がたくさん来る」のが実運用の普通の状態で、FNV-1a + `% 2^k` がいちばん弱いのもそこだった。

## 対処: 剰余の前に fmix32 を1段挟む

MurmurHash3 の最終撹拌(fmix32)を通してから割る。fmix32 は「右シフトして xor」を挟むので、上位ビットの情報が下位ビットに降りてくる。

```ts
function pickArm(ip: string, ua: string) {
  let h = fnv1a(ip + "|" + ua);
  // MurmurHash3 fmix32: 上位ビットを下位ビットへ混ぜる
  h ^= h >>> 16; h = Math.imul(h, 2246822507);
  h ^= h >>> 13; h = Math.imul(h, 3266489909);
  h ^= h >>> 16;
  return ARMS[(h >>> 0) % ARMS.length];
}
```

同じ16本で比べるとこうなる。

```
raw   % 8    8, 0, 0, 0, 0, 8, 0, 0   hit 2/8
fmix  % 8    2, 2, 1, 3, 1, 2, 3, 2   hit 8/8
```

本番で4/8だった24本の試験も、fmix32 を入れたあとは8/8になった。ランダムIPv4の8万件の結果も±2%以内のまま変わらない。同じ入力は同じ値になるので、「同じ端末は同じ飛び先」という条件もそのまま保てる。

ほかにも選択肢はある。

| やり方 | 評価 |
|---|---|
| `% 7` のように奇数で割る | 上位ビットもいくらか効くようになるが、根本的な対策ではない。飛び先の数は要件で決まるので、選べないことも多い |
| 上位ビットを使う `(h >>> 29)` | 乗算型ハッシュでは上位ビットのほうがよく混ざっている。飛び先の数が2のべき乗のときだけ使える |
| fmix32 を挟む | 3行で、飛び先の数に関係なく効く。今回はこれを採用 |
| SHA-256 などを使う(`crypto.subtle.digest`) | 確実だが非同期になる。リダイレクトの経路に入れるには少し重い |

## 検証のやり方も直した

ハッシュを直すのと同じくらい大事だったのが、検証の方法だった。

**1. 似た入力で測る。** 散らばった入力では、弱いハッシュも均等に見えてしまう。同じIPに固定して User-Agent を1〜2文字ずつ変えるなど、本番でいちばん起こりやすい形の入力で測る。

**2. 偏りの%ではなく「0件の飛び先がないか」を見る。** 人に振り分ける用途では、平均±数%の偏りよりも「自分のところにだけ1件も来ない」ほうがずっと困る。

**3. 件数が少ないと、正しいハッシュでも0件は出る。** これは見落としやすい。24件を8つに振り分けると、**理想的なハッシュでも約30%の確率で、どこか1つが0件になる**(包除原理で計算すると 0.297)。

```js
// m 件を n 個に一様に振ったとき、どこかが0件になる確率
function pEmpty(m, n) {
  let p = 0, c = 1;
  for (let j = 1; j <= n; j++) {
    c = c * (n - j + 1) / j;             // C(n, j)
    p += (j % 2 ? 1 : -1) * c * ((n - j) / n) ** m;
  }
  return p;
}
pEmpty(24, 8); // 0.297
pEmpty(48, 8); // 0.013
pEmpty(80, 8); // 0.000...
```

つまり24本の試験で「8/8人に当たった」「3人が0件だった」と言っても、それだけでは良し悪しを決められない。今回 raw の結果を「壊れている」と言い切れたのは、**8本ずつ2か所にきれいに集まる** という確率的にありえない形をしていたからだ。合否を件数で決めたいなら、8分割なら80件以上は流すべきだった。

## 教訓

- **`hash % 2^k` は、ハッシュの下位 k ビットしか使わない。** FNV-1a のような「xor と乗算」だけのハッシュは、下位ビットが入力の下位ビットでしか決まらない。上位ビットだけが違う入力(`'0'` と `'8'`、`'1'` と `'9'` など)は同じバケットに入る
- **剰余を取る前に fmix32 を挟む。** 3行で済み、決定性(同じ入力 → 同じバケット)も変わらない
- **均等さの検証は「似た入力」で行う。** ランダムな入力は、弱いハッシュの弱さを隠してしまう
- **0件判定には件数が要る。** 24件を8分割すると、正しい実装でも3割の確率で0件の箱が出る。必要な件数を先に計算してから試験する

印刷した QR コードは刷り直せない。今回は配る前に気づけたが、配ったあとに「自分の飛び先にだけ1件も来ない」と言われても直す手段がなかった。振り分けのような地味な処理ほど、本番で起こりやすい入力で一度は測っておくべきだった。
