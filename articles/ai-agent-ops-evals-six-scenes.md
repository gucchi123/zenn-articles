AIエージェントに約30の発信（ブログ・YouTube・SNS）を任せています。これまでは、失敗が出るたびに規則を1つ足して直してきました。

Anthropic の公式ブログ「Automating eval design and hillclimbing with Claude」と、それを解説した動画を見て、この直し方そのものを測ってみることにしました。要点は4つです。

- 本番に近い問題で評価する
- 問題を **train（改善中に見せる）** と **test（最後まで見せない）** に分け、**両方で上がった修正だけ残す**
- 失敗例をそのまま継ぎ足すと、評価に過剰適合する
- 伸びないときは、直す前に失敗を原因ごとに分類する（評価の側が壊れていることもある）

1日で6つの場面に入れました。先に結論を書くと、**いちばん大きかったのは「直すべき場所が、思っていたのと逆だった」こと**です。

![eval を入れる前と後](/images/ai-agent-ops-evals-six-scenes.png)

## 共通のやり方

- 正解は**本番の記録**から取る。過去の判断（送った・見送った・手直しした）、実際に公開してしまった誤り、実際の障害、検索や視聴の結果
- **日付で train / test を切る**。新しい期間で効くかを見るため
- 採用条件は「train と test の**両方で**良くなる」。片方だけ上がる修正は入れない

## 1. SNS返信：直すべきは下書きではなく「相手の選び方」だった

各媒体の返信候補キューに残っていた判断443件を評価セットにしました。

| | train（〜9/20） | test（9/21〜） |
|---|---|---|
| 下書きの送れる率（相手が良かった中で、そのまま送れた） | 65% | **94%** |
| 相手の当たり率（拾った相手が返信してよい人だった） | 66% | **48%** |

下書きの質は上がっていたのに、相手の選び方が悪化していました。対象外の失敗を原因ごとに分類すると、直近は**39%が「相談ではない投稿」**（値上げへの反応、乗り換え済みの報告、他人へのおすすめ）でした。

判定の改善を3通り試しました。

| 案 | 当たり率 train / test | 取りこぼさない率 train / test | 判定 |
|---|---|---|---|
| 今の判定 | 67% / 49% | 99% / 100% | — |
| v2 相談の言葉を必須にする | 74% / 73% | 44% / 35% | 不採用 |
| v3 推奨・済み報告・記事共有だけ落とす | 67% / 53% | 90% / 100% | 不採用（train で上がらない） |
| v4 LLM に「本人が迷っている・聞いているか」を判定させる | 78% / 69% | 32% / 41% | 方針次第 |

v4 は当たり率が大きく上がり、同じ投稿を2回判定して98%一致しました。ただ、過去に返信してきた相手の6割を落とします。過去の自分は「不満や反応」にも意図的に返信していたからです。**どちらを正解にするかは評価では決まらない方針の問題**だったので、「相談している人だけ」に決めてもらい、v4 を本番に入れました。

```python
def score(fn, rows):
    kept = [r for r in rows if fn(r)]
    good = [r for r in rows if r["outcome"] in GOOD]
    hit = [r for r in kept if r["outcome"] in GOOD]
    return len(hit) / len(kept), len(hit) / len(good)   # 当たり率, 取りこぼさない率
```

## 2. 事実チェック：答えが見えない状態で測る

実際に公開して後から直した誤り12件（旧金額・「解約金0円」・「海外70以上の国」・「9/30終了」の言い切りなど）と、直した後の正しい文12件で、公開前の関門を採点しました。

ここで1つ工夫が要りました。ある誤りは、見つかった後に事実の元帳へ「書いてはいけない形」として追記されています。今の元帳で採点すると、答えを見て解くことになります。そこで test は **見つかる前日時点の元帳** で照合しました。

| 関門 | train の誤り | test の誤り | 正しい文の誤検知 |
|---|---|---|---|
| G0 今の関門（特定の言い切りだけを見る規則） | 0/6 | 3/6 | 0/12 |
| G1 元帳と LLM で照合（2回一致96%） | 5/6 | 3/6 | 0/12 |
| **G0＋G1** | **5/6** | **6/6** | **0/12** |

規則は「その誤り」しか止めず、LLM 照合は元帳に載っている数字なら初見の誤りでも止めました。G1 の見逃しは、**その時点の元帳に載っていなかった事実**だけでした。たとえば「海外107の国と地域」は7月から元帳に正しく載っていたのに、照合する関門が無かったので、10月まで3記事に古い数字が残っていました。弱いのは元帳ではなく、元帳と照らす仕組みのほうでした。

## 3. 毎朝のレポート：静かに止まるものほど遅れる

毎朝、エージェントが運用レポートを書いています。実際の障害10件で「始まってから、レポートが初めて触れるまでの遅れ」を測りました。

| | 障害 | 平均の遅れ |
|---|---|---|
| train（〜9/20） | 4件 | 4.8日 |
| test（9/21〜） | 6件 | 0.7日 |

遅れたのは、エラーを出さずに止まる型（自動投稿の連続失敗＝5日、下書きの承認待ち＝13日）でした。そこで「止まっているもの」を機械的に集めるスクリプトを足しました。初回の実行で、ちょうどその日の午後から自動投稿が3回連続で失敗していることを**当日中に**拾えました。以前同じ原因で止まったときは、気づくまで5日かかっています。

## 4. 記事 × 検索の結果

AIメディアの記事（404本）を、Search Console の公開後28日の表示回数で評価しました。日次の記事は中央値1〜1.5回で、検索からはほとんど読まれていません。

train と test の両方で同じ向きに出たのは「本文量が多い」「FAQ がある」。**「図がある」は train では強く出たのに test では差が無く**、過剰適合の候補として外しました。

## 5. 動画の台本 × 視聴率

日次動画215本の台本と、YouTube Analytics の平均視聴率を突き合わせました。両方で再現したのは「ショートは60秒以内」と「冒頭の1文が問い」。字幕の長さは test でだけ強く出たので、採用していません。

## 6. 記事タイトル × 閲覧数

note と Tips の169本で、タイトルの型（数字入り・疑問形など）と閲覧数を見ました。**どの型も前半と後半で再現しませんでした**。差の大部分は「いつ公開したか」（アカウント全体の伸び）で説明できます。「効く型は見つからなかった」も、測ったからこそ言える結果でした。

## 7. LinkedIn の下書き × 本人が選んだか

実名で出す LinkedIn は、エージェントが下書きを作り、本人が選んで公開します。下書き64件と公開13件を突き合わせると、**公開した下書きは手直しなしで出ていて、差は「どれが選ばれたか」にありました**（採用率 train 1/35・test 11/29）。

選ばれた下書きに多かったのは、一人称「自分」（採用 55% / 不使用 11%）、「〜と思う」、最後に問いを置く形。一方で、LLM に「経験者への気づきの多さ」を採点させると、**選ばれなかった下書きのほうが点が高い**という結果でした。作る側が良いと思っている軸と、本人が選ぶ軸がずれていたことになります。口調ガイドを入れたのは直近なので、前後の比較は件数がたまってから見ます。

## やってみて分かったこと

- **直すべき場所は、測るまで分からない**。返信は下書きを直し続けていたが、悪化していたのは相手の選び方だった
- **失敗ごとに規則を足す直し方は、その失敗にしか効かない**。事実チェックの規則は既知の誤りを止めても、初見の誤りは0件だった
- **答えが見えないように測る**。事後に足した知識で採点すると、関門を過大評価する
- **評価では決まらないことがある**。「誰に返信するか」は方針の問題で、評価はその選択肢の損得を数字で見せる役だった
- **正解ラベルの偏りに注意**。判断の多くはエージェント自身が下したもので、人の判断は承認した分だけ。ここは今後、人の判断を少しずつ混ぜていく

次は、毎日の改善をこの評価の上で回します。規則を変えるときは、必ず train と test の両方を見てから入れるつもりです。
