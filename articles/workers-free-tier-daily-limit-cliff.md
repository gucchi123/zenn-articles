個人の自動化プロジェクトで、約30の媒体に貼るリンクをすべて1つの Cloudflare Workers 経由にしている。どの媒体から来たかを数えるためのリダイレクト用 Worker で、無料プランで動かしていた。

ある日、公開済みの記事約14,500本の表記を一括で書き換えた。その日、この Worker が約20時間、すべてのアクセスにエラーを返し続けた。こちらのプログラムは1つも失敗していない。気づいたのは翌朝だった。

さらに1週間後、対策として「10分おきに監視する」と記録していたスクリプトが、定期実行に登録されていなかったことに気づいた。この記事はその2つの話をまとめる。

![一括更新から上限超過、同じアカウントの別Workerの停止、定期タスクの失敗、同時再実行による設定ファイルの汚れまでの連鎖](/images/workers-free-tier-daily-limit-cliff.png)

## 症状: 全部成功しているのに、リンクだけ止まっている

一括更新そのものは成功していた。記事は書き換わっている。SNSへの投稿も通常どおり出ている。

止まっていたのは、読者がリンクを押した先だけだった。Worker はこう返していた。

```
HTTP 429
Error 1027: This website has been temporarily rate limited
```

Workers 無料プランの日次上限（10万リクエスト/日）を超えたときのエラーだ。上限に達すると、その Worker は**リセットされるまで全リクエストを拒否する**。徐々に遅くなるのではなく、ある時点から0になる。

こちらから見える数字は「クリックが減った」だけだった。失敗したタスクは無いので、失敗タスクの一覧にも出ない。

## 原因1: 一括更新が、外からの大量アクセスを呼び込んだ

後から Workers の分析 API で時間別のリクエスト数を引いた。

| 時間帯 | リクエスト数/時 |
|---|---|
| 平常 | 1〜950 |
| 一括更新の開始から3時間 | 約113,000 |
| 当日合計 | 392,050 |

最初の1時間で日次上限を超えている。

記事の本文には、この Worker を通るリンクが入っている。記事を保存すると、それをきっかけに外部の何か（保存内容の同期や、本文中のリンクを確認する仕組みなど）が、本文中のリンクを取りに来る。1本の保存で数十リクエスト、それが14,500本分。

**一括更新が叩いたのは記事のAPIだけだが、負荷は記事の外に出た。** 数日前に別の一括更新をした日も55,000件を記録していて、あと少しで同じことが起きていた。

### アクセス元は、まだ特定できていない

正直に書くと、39万件の出どころは今も分かっていない。理由は2つある。

1つ目。Workers の分析データ（GraphQL の `workersInvocationsAdaptive`）で使えたディメンションは、スクリプト名と時刻だけだった。User-Agent や ASN で絞ろうとすると unknown field が返ってきた。

2つ目は自分の設計だ。この Worker はクリックをDBに記録するが、クラウド事業者のデータセンターからのアクセスは「人間ではない」として記録しない作りにしていた。おかげでクリック数は汚れなかった。代わりに、洪水の出どころも1行も残らなかった。

計測をきれいに保つためのフィルタが、障害調査の証拠を消していた。**除外するアクセスも、集計とは別の場所に件数と出どころだけは残しておく**べきだった。

## 原因2: 上限は Worker 単位ではなく、アカウント単位

止まったのはリダイレクト用の Worker だけではなかった。

同じアカウントに、別用途のAPI中継 Worker を置いていた。日次上限はアカウント全体で数えるので、こちらも同時に 429 を返し始めた。それを使う定期タスクが3本、こういうエラーで失敗した。

```
[abort] relay not ready
```

このメッセージからは、原因が「別の Worker が上限を使い切った」ことだとは読めない。中継側の不具合を疑って、しばらく見当違いの場所を調べた。

**無料枠を共有している Worker は、1つが溢れると全部止まる。** 止まると影響が広いものと、アクセス数が読めないものを、同じアカウントに同居させていたのが構造上の問題だった。

## 原因3: 復旧後の同時再実行で、設定ファイルが汚れた

これは完全に自分のミスだ。

上限がリセットされた後、失敗していたタスクを2本、同時に再実行した。この2本は、どちらも次の手順で動くラッパーを通る。

```powershell
Copy-Item credentials.json credentials.json.bak     # 1. 退避
Set-BaseUrl credentials.json $relayUrl              # 2. 接続先を一時的な中継に書き換え
python task.py                                      # 3. 本体
Copy-Item credentials.json.bak credentials.json     # 4. 復元
```

1本だけなら問題ない。2本が重なるとこうなる。

```
A: 1.退避（本物のURLを .bak へ）
A: 2.書き換え（credentials.json は中継URL）
B: 1.退避  ← このとき credentials.json は「書き換え済み」。.bak に中継URLが入る
A: 4.復元  ← 本物に戻る
B: 4.復元  ← .bak（中継URL）を書き戻す
```

最後に残るのは、すでに削除された一時的な中継のURLだ。次にこの設定を読むタスクが、すべて存在しない接続先へ向かう。

障害の後は、止まっていたものを急いで全部動かしたくなる。同じ資源を書き換える処理は、1つずつ流すしかない。

## 対処

### 1. 上限の手前で通知する

当日のリクエスト数は GraphQL API で取れる。

```python
LIMIT = 100_000
Q = """
query($acc:String!,$start:Time!,$end:Time!){
  viewer{ accounts(filter:{accountTag:$acc}){
    workersInvocationsAdaptive(limit:200, filter:{datetime_geq:$start, datetime_leq:$end}){
      sum{requests} dimensions{scriptName datetimeHour}
    }}}}"""

def usage():
    now = datetime.datetime.now(datetime.timezone.utc)
    day0 = now.replace(hour=0, minute=0, second=0, microsecond=0)   # リセットは UTC 0時
    r = requests.post("https://api.cloudflare.com/client/v4/graphql",
                      headers={"Authorization": f"Bearer {TOKEN}"},
                      json={"query": Q, "variables": {
                          "acc": ACCOUNT_ID,
                          "start": day0.strftime("%Y-%m-%dT%H:%M:%SZ"),
                          "end": now.strftime("%Y-%m-%dT%H:%M:%SZ")}}, timeout=60).json()
    rows = r["data"]["viewer"]["accounts"][0]["workersInvocationsAdaptive"]
    return sum(x["sum"]["requests"] for x in rows)
```

集計の起点は UTC 0時にする。ローカル時刻の0時で区切ると、上限の計算とずれる。

定期実行では、使用量に加えて Worker が実際に応答しているかも見る。

```python
def check_and_notify() -> int:
    try:
        tot = usage()
    except Exception as e:
        print(f"[warn] 使用量を取得できない: {type(e).__name__}")
        tot = None
    try:
        code = requests.get(f"{WORKER_URL}/?probe=1", timeout=20).status_code
    except Exception as e:
        code = f"取得失敗 {type(e).__name__}"

    bad = 0
    if code != 200:
        notify_once(f"down{code}", f"リンクの受け口が HTTP {code}")
        bad = 1
    if tot is not None and tot >= LIMIT * 0.8:
        notify_once("over" if tot >= LIMIT else "80", f"当日 {tot:,}/{LIMIT:,}")
        bad = 1
    return 2 if bad else 0
```

気をつけた点は3つある。

- **使用量の取得に失敗しても、応答の確認は続ける。** 分析APIが落ちているときに監視ごと黙ると意味がない
- **通知は「UTC日 × 段階」ごとに1回だけ。** 10分おきに回すので、抑制しないと上限超過の日に100通以上届く
- **確認用のアクセスには印（`?probe=1`）を付け、Worker 側でクリックの計測から外す。** 監視が自分の数字を増やさないようにする

異常時は終了コード2を返す。通知が届かなくても、タスクの一覧で赤くなる。

### 2. 一括処理の前に残量を見て、分けて流す

一括更新の前に当日の使用量を確認し、余裕がある時間帯に分割する。リセット直後（UTC 0時、日本時間9時）が一番安全だ。

### 3. 同じ設定を書き換えるラッパーは直列にする

起動前に、同種のプロセスが走っていないかを見る。

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*relay*' }
```

本来は、複数のラッパーで同じロックファイルを取るべきだ。退避と復元で状態を戻す方式は、重なった瞬間に壊れる。

### 4. 有料プランを検討する

月5ドルで日次の崖そのものが無くなる。全媒体のリンクが通る場所を無料枠に載せていたこと自体、見積もりが甘かった。

## もう1つの事故: 監視は動いていなかった

ここまでの対策1は、障害の翌日に「10分おきに監視する」と記録していた。スクリプトも書いてあった。

1週間後、この件を文章にまとめ直すためにスクリプトを開いて気づいた。

- スクリプトは `print` するだけで、通知する処理が無かった
- 定期タスクに登録されていなかった

つまり、手で実行したときに数字が表示されるだけのものだった。「10分おき」は、スクリプトの引数で回数と間隔を指定できるという意味でしかなく、誰もそれを起動していなかった。

1週間、監視があると思い込んで過ごしていた。その間に一括更新をもう一度やっていたら、同じことが起きて、同じように翌朝まで気づかなかったはずだ。

通知と終了コードを実装し、定期タスクに登録したのはその日だ。登録後、タスクの一覧に名前があること、最終実行時刻が進んでいることを確認した。

## 教訓

- **無料枠の日次上限は、坂ではなく崖になっている。** 超えた瞬間から、リセットまで全リクエストが落ちる。しかも呼び出す側のプログラムは何も失敗しない
- **一括処理の負荷は、処理した対象の外に出る。** 保存をきっかけに外部が何を取りに来るかまで考える。本文中のリンクが自分のサーバーを指しているなら、保存の数だけ自分に返ってくる
- **上限の単位を確認する。** Worker 単位ではなくアカウント単位なら、無関係な Worker も一緒に止まる。そのときのエラーメッセージは、本当の原因を指していない
- **計測から除外するアクセスも、件数と出どころは別に残す。** きれいな数字と、調査できることは両立させる
- **退避→書き換え→復元の方式は、同時実行で壊れる。** 障害後の再実行ほど、一斉に流したくなるので危ない
- **「対策を記録した」と「対策が動いている」は別のことだ。** 対策を書いたら、その場でタスクの一覧と最終実行時刻を見る。記録だけが残ると、対策が無い状態より悪い。あると思って行動するからだ
