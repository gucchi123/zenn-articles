個人のプロジェクトで、複数の媒体への投稿を自動化して毎日回している。ブログ、SNS、動画、音声配信で、定期タスクは145本ある。

先日、全媒体の稼働状況をまとめて監査した。「どこかで止まっていないか」を確かめるためだ。普段は Task Scheduler の戻り値を見ていて、失敗が続いているタスクは検知できるようにしてある。その画面は概ね緑だった。

それでも3つの媒体が止まっていた。それぞれ **4週間、6日、3か月**。どれも戻り値では気づけない止まり方だった。

![タスクは成功しているのに投稿が出ていない、3つの型](/images/rc0-three-stall-patterns.png)

## 型1: 在庫を使い切って、黙ってスキップする

1日5枠で記事を投稿している媒体が、6日間止まっていた。

ログを見ると、5枠すべてにこう出ていた。

```
[在庫切れ] トピックをすべて公開済み — 本スロットはスキップ
{"status": "ALL_TOPICS_USED", "total": 180, "used": 180}
```

トピックのリストが180本で、180本とも使い終わっていた。スクリプトとしては正しい。投稿するものが無いのに無理やり投稿したら、それこそ事故になる。だから `exit 0` で正常終了する。

問題は、**この「正常終了」が6日続いても誰も気づかない**ことだった。タスクは毎日5回動いて、5回とも成功している。失敗タスクの一覧には出てこない。

在庫が尽きる系の処理は、「残りいくつ」を外に出しておくべきだった。残数が閾値を割ったら通知する、くらいで十分だ。

## 型2: 出力先が無く、末尾の `exit 0` が握り潰す

こちらは3か月動いていなかった。1日1回の写真投稿タスクで、最後に成功した記録が3か月前で止まっている。

タスクの登録内容はこうなっていた（PowerShell の引数）。

```powershell
-Command "& 'python.exe' 'script.py' *> 'logs\output.log'; exit 0"
```

`logs` ディレクトリが存在しなかった。`*>` のリダイレクトは書き込み先を開けずに失敗する。にもかかわらず、末尾の `exit 0` が戻り値を 0 で上書きしてしまう。

`exit 0` は、以前どこかで「タスクが赤くなるのが嫌」という理由で足したものだった。赤くならないので、3か月気づかなかった。ログが無いので、ログを見に行っても何も分からない。

対処自体はディレクトリを1つ作るだけで終わった。問題は気づくまでの3か月のほうだ。**タスクの引数に `exit 0` が入っているものは、戻り値を信用してはいけない。**

## 型3: 前段のタスクが、そもそも登録されていない

一番長く止まっていたのがこれで、4週間。週1回の配信が、4週分まるごと出ていなかった。

こちらは戻り値が 0 ではなく 3 だった。ログにはこう出ている。

```
[abort] 本文が前週以前のまま (--force-stale で強制実行可)
```

配信内容が前週のまま更新されていないので、古い内容を送らないように自分で中止していた。安全側の設計としては正しい。

では、なぜ本文が更新されないのか。調べたら、**本文を生成するスクリプトを定期実行するタスクが、どこにも登録されていなかった**。

処理は2本に分かれていた。

1. 配信本文を生成する（週次）
2. 生成された本文で配信を予約する（週次・月曜 09:00）

登録されていたのは 2 だけだった。おそらく最初は本文を手で書いていて、後から生成スクリプトを作ったときに、タスク登録を忘れたのだと思う。2 は毎週律儀に動いて、毎週律儀に「本文が古い」と中止していた。

戻り値が 3 なので、失敗としては検知できるはずだった。実際には**毎週同じ値が並んでいるので、「いつものやつ」として視界から外れていた**。ずっと赤いものは、赤くないのと同じになる。

修正は、前段のタスクを登録して、後段の30分前に置いた。合わせて、**「A を作る」と「A を使う」が別タスクに分かれている箇所は、同じ登録スクリプトに並べて書く**ようにした。片方だけ登録される事故を、ファイルの見た目で防ぐためだ。

## 共通しているのは「失敗していない」こと

3つとも、エラーで落ちたわけではない。**やることが無い、書き込めない、前提が揃っていない**という理由で、何もせずに終わっていた。

戻り値が答えているのは「プロセスが落ちたか」だけで、「仕事をしたか」ではない。この2つは別物なのに、監視は前者だけを見ていた。

そこで、稼働の判定を2本立てにした。

| 見るもの | 分かること |
|---|---|
| 戻り値の連続失敗 | 落ちているタスク |
| **成果物の最終日**（投稿履歴・state の最終更新日） | 落ちずに止まっているタスク |

後者は、各媒体の `post_history.json` や state ファイルの最終日を並べて、期待する頻度と突き合わせるだけでいい。実装は30行ほどだが、今回の3つはすべてこちらで見つかった。

## おまけ: 監査スクリプト自体が動いていなかった

この監査に使っている自作スクリプトを手元で実行したら、いきなり構文エラーで落ちた。

```
print(f"      最後の成功={last_ok or "記録なし"}  直近実行={last or "?"}")
                                     ^^^^
SyntaxError: f-string: expecting '}'
```

f-string の中で同じ種類のクォートを使っている。これは Python 3.12 以降なら通り、3.11 では構文エラーになる。定期タスクは 3.12 を明示的に指定して動かしていたので、タスクとしては動き続けていた。**手で叩いたときだけ落ちる**状態で、それに気づいていなかった。

「監視の仕組みが動いているか」を監視するものは無い。せめて、手で叩いたときに同じように動くかは確かめておきたい。

## まとめ

- 戻り値は「落ちたか」しか答えない。**稼働は成果物の最終日で見る**
- 在庫切れ・スキップ系は、残数を外に出す
- タスクの引数に `exit 0` があるものは、戻り値を信用しない
- 「A を作る」「A を使う」が2本に分かれていたら、**両方が登録されているか**を確かめる
- ずっと同じ失敗が並んでいるものは、視界から外れる。連続回数を出して気づけるようにする
