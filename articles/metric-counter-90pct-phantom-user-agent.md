個人で運用している流入計測で、「クリック348件なのにコンバージョン0」という経路がありました。348人が来て誰も次に進まないなら、遷移先のフローが壊れている——そう判断して、離脱ポイントの調査を始めかけたところで、前提そのものが幻だったと気づいた話です。

## 構成

- 流入リンクは Cloudflare Workers のリダイレクタを経由し、クリックごとに D1 (SQLite) にログを書く
- ダッシュボード用には `click_count` という**カウンタ列**をインクリメントしている
- 別テーブルに生ログ (`user_agent`, `ip`, `created_at` 付き) も残している

日々見ていたのはカウンタの方でした。カウンタは軽くて速い。ただし**リダイレクトを踏んだ「何か」を全部数える**という仕様で、それが誰なのかは見ていません。

## 生ログを User-Agent で仕分けたら

調査の最初の一歩として、カウンタではなく生ログを集計し直しました。

```sql
SELECT ref_code,
       SUM(CASE WHEN user_agent IS NULL OR user_agent LIKE 'WordPress%'
                 OR user_agent LIKE '%bot%' THEN 1 ELSE 0 END) AS auto,
       SUM(CASE WHEN user_agent LIKE 'Mozilla%'
                 AND user_agent NOT LIKE '%bot%' THEN 1 ELSE 0 END) AS human
FROM ref_tracking GROUP BY ref_code;
```

結果、問題の経路は **348件中338件が UA null または `WordPress/7.0`**。実ブラウザは10件でした。

![カウンタ348の中身をUAで仕分けた実像](/images/metric-counter-phantom.png)

## 幻の発生源は「自分のデプロイ」

`created_at` の分布を見ると、338件のうち299件が**ある1日に集中**していました。その日は何をした日か。ブログ全記事（約300本）に流入リンクのブロックを一括挿入した日です。

CMS（WordPress）は記事更新時にリンクの検証やプレビュー取得を行うことがあり、その HTTP リクエストがリダイレクタを通過して、1記事1カウント、300記事分のクリックが刻まれていました。UA が `WordPress/7.0; https://…` のものは `wp_remote_get` のデフォルト UA そのものです。

つまり「348クリックで転換0」の実像は「**実クリック10件で転換0**」。この母数なら転換0は異常でも何でもありません。実際、別経路では実6クリックから1件転換しており（17%）、遷移先のフローは正常に機能していました。

## 何が危なかったか

**存在しない断層を修理するところだった**、という点に尽きます。

- カウンタを信じたまま進めば、正常なフローを「壊れている」と誤診して改修し、たぶん本当に壊していた
- 「この経路は流入が太い」という判断もカウンタ由来だったので、投資配分まで歪んでいた

計測の帳簿（カウンタ）と成果物（生ログ）が乖離する事故は今回が初めてではなく、それでもまた踏みました。カウンタは**設計した時点の想定トラフィック**しか正しく数えません。想定外のアクセス（自分のデプロイ、監視、クローラ）は、カウンタからは人間と区別がつかない形で混ざります。

## 再発防止としてやったこと

1. **読み出し側を生ログ+UA仕分けに切り替えた**。カウンタは廃止せず「参考値」に降格
2. 週次レポートの該当欄は human 列だけを使うようにスクリプト化
3. 教訓のルール化: **カウンタ系の指標は、採用する前に一度 UA と日付分布を見る**。1日に数百件の集中は自動プロセスの型

計測値がおかしいとき、疑う順番は「フロー→相手→計測そのもの」ではなく、**計測そのものが最初**でよかったのだと思います。カウントの定義を1回も検算していない数字は、まだ事実ではありません。
